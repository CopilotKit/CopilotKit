The short answer

Inspector has no direct Intelligence client. It receives a live CopilotKitCore, then uses four separate ingress paths.

Runtime discovery supplies capabilities and connection facts. Inspector metadata supplies trusted commercial display data. Thread and Memory stores call real Runtime endpoints. Agent subscriptions supply the live event, message, and state stream.

4 independent data planes meet in the Inspector UI
1

Core snapshot

Agents, tools, context, catalog components, Runtime status, Runtime URL, and current capability flags.

2

Discovery + metadata

/info describes the Runtime. A separate optional request retrieves trusted Inspector metadata.

3

Service stores

Thread and Memory stores use REST for snapshots and Phoenix channels for managed realtime updates.

4

Agent events

AG-UI subscriptions feed events, messages, tool calls, state, errors, reasoning, and activity into Inspector.

Most important boundary Inspector metadata is display-only. It can change the Home hero, plan label, usage, and action links. It does not grant Threads or Memory access. Real endpoint capability and server authorization remain authoritative.

End-to-end system map

Solid arrows carry operational state or data. Dashed arrows carry descriptive metadata. The browser never calls Ops directly.

What happens from mount to live data

Provider render

Construct one stable Core

The React provider supplies Runtime URL, transport, headers, credentials, agents, tools, and component catalog. It calls connect() after commit.

Client only

Load the Inspector custom element

@copilotkit/web-inspector is imported after mount to keep SSR stable. The exact Core object is assigned to the element.

Handshake

Fetch /info

Core learns agent descriptions, per-agent capabilities, Intelligence websocket URL, thread endpoint capabilities, Runtime license status, and whether Inspector metadata exists.

Background

Fetch metadata independently

Only after connection and capability advertisement, Core makes the optional metadata request. Headers, credentials, transport, or URL changes invalidate stale requests. The browser and Runtime each enforce a five-second timeout.

Attach

Subscribe to Core and every agent

Inspector snapshots existing agents, context, tools, thread stores, and metadata, then subscribes for changes and per-thread run clones.

On demand

Create service stores only when needed

Inspector owns Thread stores when the app has not registered them. The Memory store is intentionally lazy and starts only when the user opens Learning, including a persisted Learning selection.

Managed deployment

App API derives scope from validated Runtime authentication, obtains durable commercial truth from an internal Ops projection, and combines it with App API identity and usage. The SDK receives only a safe display contract.

Self-hosted deployment

App API reads the local signed license checker for the metadata license state. There is no managed billing action because Ops is not the source of truth.

The Home status is a summary, not a probe.Home considers Intelligence connected when metadata says the license is valid. If metadata is unknown, it falls back to the /info Intelligence marker. Each service tile then adds its own capability flag.

Threads: capability first, identity at the server

The Threads pane is always in navigation. It becomes operational only when Runtime discovery says listing is available.

1 · Capability

Runtime advertises list and inspect for Intelligence or a local runner that supports thread endpoints. Only managed Intelligence advertises mutations and realtime metadata.

2 · Snapshot

A registered app Thread store is reused. Otherwise Inspector creates one per agent and calls Runtime-relative GET /threads?agentId=….

3 · Realtime

The list response includes a join code. POST /threads/subscribe returns credentials for the user_meta Phoenix topic, which upserts or removes rows.

list Inspector → Core ThreadStore → Runtime /threads → Intelligence App API → scoped database query
live ThreadStore → Runtime /threads/subscribe → Redis token → Phoenix thread_metadata
detail Inspector → Runtime /threads/:id/{messages,events,state} → App API or local runner
User scope is not accepted from the browser.The Runtime calls identifyUser. Intelligence validates the Runtime API key, organization, project, app user, and thread ownership before reading data.

Timeline detail

Selecting a real thread eagerly fetches metadata, events, and messages. State is available through its own endpoint. A 501 response means that an inspect surface is unsupported.

View in app

A development-only window CustomEvent bridge asks an official chat component to load the selected thread. Request IDs pair the request and result, and failure restores the previous chat.

“Learning” is currently a Memory browser

The visible pane label is Learning, but its internal menu key is memories and its data comes from the Core Memory store.

What opens the data path

Attaching Inspector does not touch core.getMemoryStore(). The first Learning-tab activation creates the singleton store, starts it, lists memories, requests realtime credentials, and subscribes to store selectors.

A persisted selectedMenu: "memories" counts as activation when Core attaches.

What the pane can do

It displays user and project memories, loading and error states, source-thread links, invalidation state, realtime health, and semantic recall results.

POST /memories/recall returns ranked results through the same Memory store.

snapshot Learning pane → lazy Core MemoryStore → Runtime /memories → App API requireMemoryEntitlement → memory service
realtime MemoryStore → Runtime /memories/subscribe → user and optional project Phoenix topics
recall MemoryStore → Runtime /memories/recall → entitled memory recall
There are two different product gates.The Memory API uses the memory entitlement. The learning runtime uses LEARNING_RUNTIME_ENABLED, organization rollout, and self_learning. The latter controls learning-container assignment and harvest behavior; it does not hide or unlock the Inspector pane.
Current optimistic-state edge._memoriesAvailable starts as true. Until the user activates Learning and the real route answers, Home can show Memory as enabled whenever Intelligence is considered connected. Responses 404, 422, or 501 then degrade to “unavailable”; an entitlement denial is a real error.

Failure isolation and stale-state rules

Metadata fails soft

A timeout, non-OK response, 204, malformed payload, or upstream Ops failure becomes absent or partial metadata. Runtime connection and thread work continue.

Metadata requests are generation-safe

A URL, header, credential, or transport change aborts the old request. Late responses cannot overwrite data for a newer Core configuration.

Threads clear on disconnect

Inspector immediately clears cached thread rows and scheduled usage refresh when Runtime leaves the connected state.

Memory distinguishes absence from error

404, 422, and 501 mean the optional route is unavailable. Authorization failures and network failures remain visible errors.

Per-agent discovery is isolated

One agent failing to report capabilities does not fail the entire /info response.

Realtime does not replace snapshots

REST establishes canonical rows. Realtime updates them. Thread message-version signals trigger a canonical message refetch rather than trusting a partial payload.

Audit findings

Boundary is sound

Commercial projection stays server-side. Browser code receives a validated, safe subset and cannot use it as authority. Ops is behind App API and never exposed to the SDK.

Service authority is sound

Thread identity and ownership are enforced downstream. Memory is guarded by its actual feature entitlement. Metadata loss cannot accidentally grant access.

Naming conceals the split

The “Learning” label suggests the self_learning product gate, but the pane is technically a Memory client governed by memory. This is the largest conceptual trap in the implementation.

Home Memory status can be optimistic

Availability defaults to true until first pane activation. This preserves laziness, but means Home is not definitive before a Memory route probe.

Navigation is discoverability-first

Threads and Learning remain visible when locked. Frontend Tools and Capabilities are data-driven and hidden when empty.

Core is the integration seam

Inspector stays framework-neutral because React only mounts the custom element. The Inspector’s operational contract is the live Core object, not React context or Intelligence APIs.

Recommended mental modelTreat Inspector as a projection over Core. Treat /info as discovery, Inspector metadata as trusted description, and the Thread/Memory routes as authority. “Learning” is presentation vocabulary over Memory today.
