<Steps>
  <Step>
    ### Install the Cloudflare Agents AG-UI adapter

    ```bash
    npm install agents @ag-ui/cloudflare-agents ai
    ```

  </Step>
  <Step>
    ### Ask for the human with a frontend tool

    The simplest route is an ordinary frontend tool. Register it in the
    browser with `useHumanInTheLoop`, or with `useFrontendTool` and an `async`
    handler that resolves once the user has answered. `run.streamTextOptions()`
    hands the tool to the model on every run. When the model calls it, the run
    ends and the browser asks the user. The answer goes back with the next
    request as the call's result, and the model continues from there.

    That leaves the agent with one job: knowing the tool exists and when to
    call it. Name it in the instructions you pass to `run.streamTextOptions()`,
    or a model that is never told about it may answer in prose.

  </Step>
  <Step>
    ### Or pause a server tool with tool approval

    When the backend decides it needs the user, put the tool under the AI
    SDK's tool approval: `toolApproval: { schedule_meeting: "user-approval" }`
    on `streamText` with AI SDK v7, or `needsApproval: true` on the tool with
    AI SDK v6. The AI SDK stops before the tool runs, and the adapter ends the
    AG-UI run with an interrupt for that call, which `useInterrupt` renders.
    The interrupt's `reason` is `"tool_approval"`, its `metadata` carries
    `tool_name` and the parsed `tool_input`, and its `responseSchema` asks for
    `{ "approved": boolean }`.

    The showcase's agents list the tools that need approval in
    `approvalRequired`, and the shared run loop turns that list into
    `toolApproval`:

    The next request resumes the interrupt. Only a no denies the call: a
    resume entry with `status: "cancelled"`, a payload of `false`, or
    `{ "approved": false }` tells the model the tool did not run, and a
    `reason` in the payload becomes the reason the model reads. Any other
    answer, `{ "approved": true }` among them, runs the tool before the model
    is called again.

  </Step>
  <Step>
    ### Hand the tool more than a yes or no

    Since any answer but a no approves the call, the page can resume with what
    the user chose. The showcase's time picker resumes with the chosen slot,
    or with `{ cancelled: true }` from its Cancel button. Neither is a no, so
    `schedule_meeting` runs either way and reads the answer with
    `run.resumePayload(toolCallId)` (`execute` gets the `toolCallId` as its
    second argument). An `approved` that is not a boolean is refused.

<Callout type="info" title="The Durable Object guards the approval">
  The agent records in its Durable Object which calls it paused, so a resume
  can only approve a call the model actually made, and an approved tool runs
  at most once, even if a retry answers the same approval again. Answer every
  waiting approval: a request that leaves one unanswered is refused with a
  `RUN_ERROR` (code `INVALID_RESUME`) before the model runs. For a tool whose
  effect must never repeat, also pass the tool call id (`execute`'s second
  argument has `toolCallId`) as the idempotency key of the API it calls.
</Callout>
