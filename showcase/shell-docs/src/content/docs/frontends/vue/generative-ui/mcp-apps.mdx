## What is this?

MCP Apps are MCP servers that expose tools with associated UI resources. When the agent calls one of these tools, CopilotKit automatically fetches the resource and renders the UI component in the chat; no additional frontend code required.

  **Free course:** See this pattern built end-to-end in [Build Interactive
  Agents with Generative
  UI](https://www.deeplearning.ai/short-courses/build-interactive-agents-with-generative-ui/)

  full Generative UI spectrum (Controlled, Declarative, and Open-Ended).
</Callout>

Key benefits:

- **Zero frontend code** — UI components are served by the MCP server
- **Full interactivity** — components can use HTML, CSS, and JavaScript
- **Secure sandboxing** — content runs in isolated iframes
- **Thread persistence** — MCP Apps are stored in conversation history and restored on reconnect

## Wire the runtime to your MCP server(s)

A single `mcpApps.servers` entry on the runtime is all it takes. The runtime auto-applies the MCP Apps middleware to every registered agent: each time an agent calls a tool backed by an MCP UI resource, the middleware fetches the resource and emits an `activity` event that Vue's built-in `MCPAppsActivityRenderer` renders inline in the chat as a sandboxed iframe.

```ts title="server.ts"
import { CopilotRuntime } from "@copilotkit/runtime/v2";

const runtime = new CopilotRuntime({
  agents: { default: agent },
  mcpApps: {
    servers: [
      {
        type: "http",
        url: "https://mcp.example.com/mcp",
        serverId: "support-tools",
      },
    ],
  },
});
```

<Callout type="info" title="Always pin a serverId">
  In production, always provide a stable `serverId`. Without it, CopilotKit
  hashes the server URL, and a URL change (for example between environments)
  silently breaks restoration of MCP Apps persisted in earlier conversation
  threads.
</Callout>

## No frontend renderer needed

Unlike custom activity types, the MCP Apps renderer is already registered by `CopilotKitProvider` out of the box. A plain `<CopilotChat />` is enough; no manual renderer wiring is required.

```vue title="src/App.vue"
<script setup lang="ts">
import { CopilotChat, CopilotKitProvider } from "@copilotkit/vue/v2";
</script>

<template>
  <CopilotKitProvider runtime-url="/api/copilotkit">
    <main style="height: 100dvh"><CopilotChat /></main>
  </CopilotKitProvider>
</template>
```

## Sandbox and widget storage

Each MCP App runs in a sandboxed iframe with an opaque origin. A widget can't
read your page's cookies, storage or DOM. It can't read responses from your
APIs either, unless an API allows cross-origin requests, for example with
`Access-Control-Allow-Origin: *`. It can still send requests, so protect
state-changing endpoints against cross-site request forgery as you would for
any other site. The trade-off is that the widget can't use `localStorage`,
`sessionStorage`, `IndexedDB` or cookies of its own either.

Requests a widget makes that need CORS, such as `<script type="module">` and
`fetch`, are sent with `Origin: null`. Serve public widget assets with
`Access-Control-Allow-Origin: *`. Classic `<script src>` tags don't need CORS.
To avoid CORS entirely, bundle the widget into a single HTML file, as the
[ext-apps examples](https://github.com/modelcontextprotocol/ext-apps/tree/main/examples)
do with `vite-plugin-singlefile`.

The MCP Apps spec pairs `allow-same-origin` with a sandbox served from a
separate origin. By default CopilotKit loads the sandbox inline, so it leaves
`allow-same-origin` off rather than give widgets your page's origin.

### Serve the sandbox from a separate origin

To give widgets working storage without exposing your page, serve the sandbox
proxy from a separate domain, such as `https://example-sandbox.com`.
This is the setup the MCP Apps spec describes.

1. Copy `mcp-apps-sandbox-proxy.html` from `@copilotkit/mcp-apps-renderer`
   (`node_modules/@copilotkit/mcp-apps-renderer/dist/`) to the root of the
   sandbox origin. It's a static file, so any static host works.
2. Point CopilotKit at that origin:

```vue title="Separate sandbox origin"
<script setup lang="ts">
import { CopilotChat, CopilotKitProvider } from "@copilotkit/vue/v2";
</script>

<template>
  <CopilotKitProvider
    runtime-url="/api/copilotkit"
    :mcp-apps="{ sandboxOrigin: 'https://example-sandbox.com' }"
  >
    <CopilotChat />
  </CopilotKitProvider>
</template>
```

To serve the file from another path, pass its full URL instead, such as
`https://example-sandbox.com/mcp/proxy.html`.

Widgets then run with the sandbox origin. They can use `localStorage`,
`IndexedDB` and cookies, but can't reach your page, and CopilotKit only
accepts messages from that origin. CopilotKit refuses to load a widget if
`sandboxOrigin` is your page's own origin.

- Use a separate domain that serves nothing else, such as
  `example-sandbox.com` for an app on `example.com`. Avoid a subdomain of your
  site, such as `sandbox.example.com`. It is same-site with your page, so
  browsers send your `SameSite` cookies on a widget's requests to your APIs,
  and a widget can set cookies for `example.com` that your app then reads.
- All widgets share the sandbox origin, so they share its storage too. A
  widget from one MCP server can read what another one stored.
- To stop other sites from embedding your proxy, send
  `Content-Security-Policy: frame-ancestors https://app.example.com` with it.
- The proxy applies each widget's CSP from its `_meta.ui.csp`, the same policy
  as the inline sandbox. If you add a CSP header to the proxy, keep it at
  least as permissive, since widgets inherit it as well.

### Restore same-origin access

If you can't serve a separate origin, and you wrote a widget yourself that
needs storage, you can restore `allow-same-origin` on the inline sandbox:

```vue title="Trusted widget configuration"
<script setup lang="ts">
import { CopilotChat, CopilotKitProvider } from "@copilotkit/vue/v2";
</script>

<template>
  <CopilotKitProvider
    runtime-url="/api/copilotkit"
    :mcp-apps="{ allowSameOriginFallback: true }"
  >
    <CopilotChat />
  </CopilotKitProvider>
</template>
```

<Callout type="warn" title="Only for widgets you trust">
  With `allowSameOriginFallback`, every MCP App runs with your page's origin.
  Any connected MCP server's widget can then read your cookies and storage and
  act as the signed-in user. Don't enable it if you connect third-party MCP
  servers.
</Callout>

## Transport types

The middleware supports two transport types:

### HTTP

Use this format to connect to an MCP server that accepts standard HTTP requests:

```typescript
{
  type: "http",
  url: "http://localhost:3101/mcp",
  serverId: "my-http-server"
}
```

### SSE

Use this format to connect to an MCP server that streams events over a persistent connection:

```typescript
{
  type: "sse",
  url: "https://mcp.example.com/sse",
  headers: {
    "Authorization": "Bearer token"
  },
  serverId: "my-sse-server"
}
```

Keep credentials on the runtime; do not expose private MCP tokens in Vue code.
