Connecting a runtime to Intelligence takes two things: construct a
`CopilotKitIntelligence` client with your project API key, and pass it to your
runtime as `intelligence`. The runtime reads the key from the client you pass,
not from the environment.

This page is that wiring step. For what the platform is and why you would use it,
see the [CopilotKit Intelligence overview](/intelligence/overview) and the
[architecture page](/intelligence/intelligence-platform).

## Before you start

You need a project API key. Either provision one with the CLI:

```bash title="Terminal"
npx copilotkit login
npx copilotkit project select
```

`project select` writes a project-scoped key to `.env` as `CPK_INTELLIGENCE_API_KEY`.
You can also copy a key from the
[cloud-hosted dashboard](/intelligence/managed-intelligence-platform).

```bash title=".env"
CPK_INTELLIGENCE_API_KEY=cpk-...
```

<Callout type="warn">
  This is a server-side secret. Do not give it a `NEXT_PUBLIC_` or `VITE_`
  prefix — that ships it to the browser.
</Callout>

### Next.js apps in a subdirectory

Next.js loads `.env*` files from the Next.js app directory. If your app is in
`web/` and the CLI writes the key to a shared `.env` at the repository root,
`process.env.CPK_INTELLIGENCE_API_KEY` will be unset unless the server process
loads that file.

For a shared root `.env`, read it in the Next.js config, so the values are in
the environment before anything serves a request (Node.js 20.12 or later):

```ts title="web/next.config.ts"
process.loadEnvFile("../.env"); // resolved against the directory you run Next.js in

export default {};
```

This covers `dev`, `build` and `start` alike, including a bare `npm run dev`,
and it leaves a real environment variable alone: a hosted deployment that sets
the key itself keeps its own value.

<Callout type="warn" title="Do not pass `--env-file` to the Next.js binary">
  `node --env-file=../.env ./node_modules/next/dist/bin/next dev` looks
  equivalent and is not. Next.js starts a child process and copies the flags it
  was given into `NODE_OPTIONS`, where Node refuses this one: `--env-file= is not
  allowed in NODE_OPTIONS`. The parent reads the file, the child that serves your
  app never starts, and the failure names `NODE_OPTIONS` rather than anything you
  configured. Reading the file in the config passes no flag at all, so there is
  nothing for the child to reject.
</Callout>

If the app owns its environment instead, put the key in `web/.env.local`.
On a hosted deployment, set it in the server's environment settings. Load the
key before constructing `CopilotKitIntelligence`; the `!` in the example below
only affects TypeScript and does not load or validate an environment variable.

## Wire the runtime

Construct the client once and pass it to `CopilotRuntime` as `intelligence`.

```ts title="app/api/copilotkit/[[...slug]]/route.ts"
import {
  CopilotRuntime,
  CopilotKitIntelligence,
  createCopilotRuntimeHandler,
} from "@copilotkit/runtime/v2";

const intelligence = new CopilotKitIntelligence({
  // apiUrl and wsUrl default to the managed platform — leave them unset.
  apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
});

const runtime = new CopilotRuntime({
  agents,
  intelligence,
  // Threads are per-user. Without this every visitor shares one history.
  identifyUser: (request) => ({
    id: request.headers.get("x-user-id") ?? "anonymous",
    name: request.headers.get("x-user-name") ?? "Anonymous",
  }),
});

export const { GET, POST, PATCH, DELETE } = createCopilotRuntimeHandler({ runtime });
```

`apiKey` is the only required field on the Intelligence client. The key scopes the project,
so there is no separate organization or project id to pass.

<Callout type="warn" title="`identifyUser` is required, not advisory">
On the runtime itself, `identifyUser` is required whenever the runtime serves a web surface —
the options type will not accept its absence. The one exception is a Channels-only runtime,
which serves no web surface and passes a non-empty `channels` array instead.
</Callout>

### Converting a runtime that already has a runner

An existing open-source runtime usually passes a `runner`, which decides where its
runs are kept. Intelligence replaces that choice: the platform keeps the runs, so an
Intelligence runtime wires `IntelligenceAgentRunner` itself and accepts no runner of
your own. The two options are mutually exclusive. Remove `runner` as you add
`intelligence`:

```ts
const runtime = new CopilotRuntime({
  agents,
  runner: new InMemoryAgentRunner(), // [!code --]
  intelligence, // [!code ++]
  identifyUser,
});
```

TypeScript rejects the pair outright, because `runner` is declared only on the SSE
options. A JavaScript caller gets the same answer when the runtime is constructed:

```text
Intelligence Runtime auto-wires its own `runner`; passing `runner` alongside
`intelligence` is not supported.
```

Keeping the runner is the other valid choice. Drop `intelligence` instead and the
runtime stays in SSE mode with the runner you control, and Threads and the Inspector
stay locked. See [AgentRunner and persistence](/backend/agent-runner) for what each
runner does.

## Confirm the credential is actually used

A build that compiles and a chat that replies both prove nothing about
Intelligence — a runtime in SSE mode does all of that with the key unread. So a
green round trip in the browser is not evidence on its own.

Confirm it from the product side instead. Open your project in the
[cloud-hosted dashboard](/intelligence/managed-intelligence-platform) and send a
message in your app. A thread should appear. If none does, the runtime never
reached the platform and is running in SSE mode, whatever the browser showed.

## Self-hosted deployments

`apiUrl` and `wsUrl` default to the managed platform. Override them **together**
or not at all — the API and realtime planes are deployed on different hosts, so
the websocket URL cannot be derived from the API URL, and setting one alone
leaves the other plane pointed at the managed host.

```ts
const intelligence = new CopilotKitIntelligence({
  apiUrl: "https://api.intelligence.internal",
  wsUrl: "wss://realtime.intelligence.internal",
  apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
});
```

Pass the bare websocket base: the client appends `/runner` and `/client` itself,
and prepends `/api` to every REST call. Passing `apiUrl: ".../api"` produces
double-prefixed `/api/api/threads`.

See [Self-host CopilotKit Intelligence](/intelligence/self-hosting) for the full
deployment path.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Chat works, no threads in the dashboard | `intelligence` was never passed to `CopilotRuntime`; the runtime is in SSE mode. |
| Opaque auth error on the first request | `CPK_INTELLIGENCE_API_KEY` is empty or belongs to a different project. |
| Socket sits in `connecting`, then "did not settle in time" | `wsUrl` overridden alone, or pointed at the API host. |
| `/api/api/...` in request logs | `apiUrl` included a `/api` suffix. |
| A type error, or a throw, naming `runner` | `runner` and `intelligence` cannot both be set. Intelligence wires its own runner. |
