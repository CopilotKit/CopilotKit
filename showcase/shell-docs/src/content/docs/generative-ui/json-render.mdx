You have a chat surface and you want the agent to draw a dashboard from a typed JSON spec. By the end of this guide, the agent will emit a `{ root, elements }` object, [`@json-render/react`](https://www.npmjs.com/package/@json-render/react) will validate it against a Zod-described catalog, and the user sees the dashboard render as a single React tree.

## When to use this

- **Structured UI with a typed contract** where the agent's output is validated against a known schema before it touches the DOM.
- **Tolerance for prose preamble + code fences** in the agent's output (json-render's parser handles them).
- **Cases where you already use json-render** elsewhere or prefer Zod-validated catalogs.

If you'd rather have a streaming progressive render rather than a one-shot validated render, see the sibling page [Hashbrown](/generative-ui/hashbrown) for the same scenario with `@hashbrownai/react`.

## Frontend

The integration point is `<CopilotChat>`'s `messageView.assistantMessage` slot. Use the **Code** tab above for the complete, framework-specific files. These demos pin `@json-render/react` and `@json-render/core` to `0.18.0`; use the same versions when copying their code. `page.tsx` provides `<CopilotKit>`, `chat.tsx` installs `JsonRenderAssistantMessage` in the chat slot, and `json-render-renderer.tsx` parses the assistant content. The runtime route differs between Strands TypeScript and Google ADK; the Code tab shows the route for the selected framework.

The renderer imports `registry` from `registry.tsx`, wraps `<Renderer spec={spec} registry={registry} />` in `<JSONUIProvider registry={registry}>`, and falls back to the normal assistant message until a valid spec arrives. `catalog.ts` defines component names and Zod prop schemas with `defineCatalog`; `registry.tsx` uses `defineRegistry(catalog, …)` to bind those names to React components. Copy both files with the renderer. The catalog and registry allow only the components the application has registered.

## Backend

The agent emits a `{ root, elements }` JSON object as the assistant message content. `root` references a top-level element id; `elements` maps each id to a `{ type, props, children }` triple matching the catalog.

```json title="example agent output"
{
  "root": "revenue-card",
  "elements": {
    "revenue-card": {
      "type": "MetricCard",
      "props": { "label": "Total revenue", "value": "$184,302", "trend": "+12%" },
      "children": ["by-region"]
    },
    "by-region": {
      "type": "BarChart",
      "props": {
        "title": "Revenue by region",
        "description": null,
        "data": [
          { "label": "North America", "value": 112000 },
          { "label": "EMEA", "value": 72302 }
        ]
      }
    }
  }
}
```

The example uses a `MetricCard` root because the registered components are `MetricCard`, `BarChart`, and `PieChart`; there is no `Stack` component. The renderer tolerates a prose preamble or code fence around the JSON, but the agent prompts ask for plain JSON. Google ADK's shared BYOC agent also emits a `ui` array for its Hashbrown demo; the JSON Render renderer reads `root` and `elements` from the same response.

## Comparing the two patterns

Both `byoc-json-render` and [`byoc-hashbrown`](/generative-ui/hashbrown) solve the same problem with two different rendering libraries. The agent contract is similar; the React glue, validation strategy, and rendering behaviour differ.
