Use a fixed schema when your agent always shows the same kind of card,
such as a flight or an order. You design the layout once (by hand, or
with the [A2UI Composer](https://a2ui-composer.ag-ui.com/)) and keep it
on the agent side. The agent tool supplies only the *data*, so the card
appears as soon as the tool returns.

How the schema is *delivered* to the runtime is the only thing that
varies between integrations:

- **Schema-loading** (including Strands TypeScript), the schema is saved
  as a `.json` file next to the agent and loaded once at startup.
- **Schema-inline** (spring-ai, ms-agent-dotnet), the schema is
  declared inline as a typed literal in source. The host language
  doesn't ship a `load_schema` JSON loader, so the structure is
  compiled in directly.
- **LLM-driven** (Mastra and Strands Python), the agent runs a secondary
  LLM call to produce the operations container per-request. The catalog
  is still fixed; the schema is generated on demand.

The examples on this page use a flight card. Use your own components
and tool.

## How it works

1. The schema is made available to the agent, either loaded from a
   JSON file at startup, declared inline, or generated per-request,
   depending on the integration.
2. The agent's `display_flight` tool receives data from the primary LLM
   (origin / destination / airline / price).
3. The tool returns an operations container with `createSurface` +
   `updateComponents` + `updateDataModel` operations.
4. The A2UI middleware finds the operations in the tool result. The
   runtime converts them to A2UI 1.0, and the browser renders the
   surface with the client catalog: four custom components (Airport,
   Arrow, AirlineBadge, PriceTag) plus the standard ones.

## Compositional schemas

The example below ships a flight card assembled compositionally from
small sub-components rather than one monolithic `FlightCard`:

```
Card
 └─ Column
     ├─ Title        ("Flight Details")
     ├─ Row          (Airport → Arrow → Airport)
     ├─ Row          (AirlineBadge · PriceTag)
     └─ Button       (Book)
```

That tree lives backend-side, as a JSON file, an inline literal, or
a per-request LLM output, depending on the integration. Components
without data bindings (like `Title` or `Arrow`) carry their value
inline. Components bound to the LLM's data (like `Airport`) reference
fields with JSON Pointer paths such as `{ "path": "/origin" }`. The
runtime converts each binding to A2UI 1.0, and the browser resolves it
before your component renders, so your component gets a plain value.

## The custom catalog

The client catalog declares the domain components (Airport, Arrow,
AirlineBadge, PriceTag). `extends: [standardUI]` adds the standard
components (Card, Column, Row, Title, Button, and more). Each name must
be the name that the schema uses.

<Steps>
<Step>
### Declare the components

```tsx title="app/flight-ui.tsx"
"use client";
import { z } from "zod";
import {
  createGenerativeUI,
  standardUI,
} from "@copilotkit/react-core/generative-ui";

export const flightUI = createGenerativeUI({
  // The catalog id that the agent writes in createSurface.
  id: "copilotkit://flight-fixed-catalog",
  extends: [standardUI],
  components: {
    Airport: {
      component: ({ code }: { code: string }) => <strong>{code}</strong>,
      description: "A 3-letter airport code, displayed large.",
      props: z.object({ code: z.string() }),
    },
    Arrow: {
      component: () => <span aria-hidden="true">→</span>,
      description: "A right-pointing arrow used between airports.",
    },
    AirlineBadge: {
      component: ({ name }: { name: string }) => <span>{name}</span>,
      description: "A pill-styled airline name tag.",
      props: z.object({ name: z.string() }),
    },
    PriceTag: {
      component: ({ amount }: { amount: string }) => <span>{amount}</span>,
      description: "A stylized price display, for example '$289'.",
      props: z.object({ amount: z.string() }),
    },
  },
});
```

Declare each prop with its plain type. A bound prop, such as `code`
with `{ "path": "/origin" }`, arrives resolved.
</Step>

### Load the schema JSON at startup

Save the component tree as `a2ui_schemas/flight_schema.json` next to the
agent. Each `{ "path": ... }` value binds a prop to the data model:

```json title="a2ui_schemas/flight_schema.json"
[
  { "id": "root", "component": "Card", "child": "content" },
  {
    "id": "content",
    "component": "Column",
    "children": ["title", "route", "meta", "bookButton"]
  },
  { "id": "title", "component": "Title", "text": "Flight Details" },
  {
    "id": "route",
    "component": "Row",
    "justify": "spaceBetween",
    "align": "center",
    "children": ["from", "arrow", "to"]
  },
  { "id": "from", "component": "Airport", "code": { "path": "/origin" } },
  { "id": "arrow", "component": "Arrow" },
  { "id": "to", "component": "Airport", "code": { "path": "/destination" } },
  {
    "id": "meta",
    "component": "Row",
    "justify": "spaceBetween",
    "align": "center",
    "children": ["airline", "price"]
  },
  { "id": "airline", "component": "AirlineBadge", "name": { "path": "/airline" } },
  { "id": "price", "component": "PriceTag", "amount": { "path": "/price" } },
  {
    "id": "bookButton",
    "component": "Button",
    "variant": "primary",
    "child": "bookButtonLabel",
    "action": {
      "event": {
        "name": "book_flight",
        "context": {
          "origin": { "path": "/origin" },
          "destination": { "path": "/destination" },
          "airline": { "path": "/airline" },
          "price": { "path": "/price" }
        }
      }
    }
```

<Step>
### Attach the tool to an existing `StateGraph`

The snippets above stop at the tool. The example agent uses
`langchain.agents.create_agent` with `CopilotKitMiddleware` (that is what
those imports are for), but the snippets do not show how it is built. If you added
A2UI to an agent you already wrote, you probably have a hand-built `StateGraph`
instead. The tool is unchanged; put it in a `ToolNode` and leave the rest of the
graph alone:

```python title="agent.py (LangGraph StateGraph form)"
from langchain_openai import ChatOpenAI
from langgraph.graph import START, MessagesState, StateGraph
from langgraph.prebuilt import ToolNode, tools_condition

# `display_flight` is the tool defined above — unchanged.
model = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none").bind_tools([display_flight])


def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}


builder = StateGraph(MessagesState)
builder.add_node("call_model", call_model)
builder.add_node("tools", ToolNode([display_flight]))
builder.add_edge(START, "call_model")
builder.add_conditional_edges("call_model", tools_condition)
builder.add_edge("tools", "call_model")

# No `checkpointer=` — the LangGraph API server owns persistence and
# rejects a custom one. See the LangGraph quickstart for the FastAPI case,
# where you host the graph yourself and do need a checkpointer.
graph = builder.compile()
```

Keep whatever system prompt your agent already has. The example agent's prompt
tells the model to call `display_flight` exactly once and stop, because the tool
result *is* the rendered card. Without it, the model tends to call the tool
again, looking for a status code.

`CopilotKitMiddleware` is a `create_agent` middleware, so it has no
`StateGraph` equivalent. The fixed-schema path does not need one: the
A2UI middleware that turns the tool result into a surface runs in the
TypeScript runtime (see [Turn off tool injection on the runtime](#turn-off-tool-injection-on-the-runtime)
below), not in the graph. Note that dropping it also drops the other things it
does (frontend-tool injection and exposing agent state to the model), so keep
`create_agent` if your agent relies on those.
</Step>
</WhenFrameworkHas>

<Step>
### Generate the schema dynamically

Mastra and Strands Python take a different route: the agent tool runs a
*secondary* LLM call with a forced tool choice that produces the
operations container per-request. The frontend catalog is still fixed
(same `Title`/`Airport`/`Arrow`/`AirlineBadge`/`PriceTag` primitives),
but the schema is built on the fly. Schema construction and render
emission happen in the same tool call.

Neither SDK ships an `a2ui.render(...)` equivalent here, so the tool
assembles the `a2ui_operations` envelope itself. In Mastra, the
operation builder is in the snippet below. In Strands Python, the
snippet imports the builder (`build_a2ui_operations_from_tool_call`)
and the catalog helpers from the demo's shared
[`tools` package](https://github.com/CopilotKit/CopilotKit/tree/main/showcase/shared/python/tools).
Copy those functions with the tool. Note the operations are *nested*
(`{ createSurface: {...} }`): a consumer dispatches on the operation
key, so a flat `{ type: "create_surface" }` shape is ignored and the
surface never paints.

### Pass the UI to the provider

```tsx title="app/providers.tsx"
"use client";
import type { ReactNode } from "react";
import { CopilotKitProvider } from "@copilotkit/react-core";
import { flightUI } from "./flight-ui";

export function Providers({ children }: { children: ReactNode }) {
  return (
    <CopilotKitProvider runtimeUrl="/api/copilotkit" generativeUI={{ ui: flightUI }}>
      {children}
    </CopilotKitProvider>
  );
}
```

In Angular, use `provideGenerativeUI({ ui })`. See
[Components and surfaces](/generative-ui/components).
</Step>

<Step>
### Turn off tool injection on the runtime

Your agent owns the tool in the fixed-schema approach, so the runtime
must not add one. Set `a2uiVersion: "0.9"` and `injectA2UITool: false`.
The runtime still finds the operations in the tool result and converts
them, with no subagent involved:

```typescript title="app/api/copilotkit/[[...slug]]/route.ts"
import { LangGraphAgent } from "@ag-ui/langgraph";
import { CopilotRuntime, createCopilotRuntimeHandler } from "@copilotkit/runtime";

const runtime = new CopilotRuntime({
  agents: {
    "a2ui-fixed-schema": new LangGraphAgent({
      deploymentUrl: process.env.LANGGRAPH_DEPLOYMENT_URL ?? "http://localhost:8123",
      graphId: "a2ui_fixed_schema",
    }),
  },
  generativeUI: {
    a2uiVersion: "0.9",
    injectA2UITool: false,
    agents: ["a2ui-fixed-schema"],
  },
});

const handler = createCopilotRuntimeHandler({ runtime, basePath: "/api/copilotkit" });

export const GET = handler;
export const POST = handler;
```

## Why compositional beats monolithic

A single big `FlightCard` component would be faster to write but would
lock the design in place. Assembling the card from Card / Column /
Row / Title / Airport / Arrow / AirlineBadge / PriceTag gives you:

- **Reusable primitives** the same `Airport` renderer works in
  search results, booking confirmations, and future seat maps.
- **Schema-level design iteration** re-arranging rows or swapping a
  badge requires only a JSON edit; the renderer code is untouched.
- **A2UI Composer compatibility** hand-written and Composer-built
  schemas share the same primitive vocabulary.

## Action handlers (reference)

The flight card's **Book flight** button declares its action in the schema:

```json
{
  "id": "bookButton",
  "component": "Button",
  "variant": "primary",
  "child": "bookButtonLabel",
  "action": {
    "event": {
      "name": "book_flight",
      "context": {
        "origin": { "path": "/origin" },
        "destination": { "path": "/destination" },
        "airline": { "path": "/airline" },
        "price": { "path": "/price" }
      }
    }
  }
}
```

When the user clicks the button, CopilotKit sends the action to the agent
in a new run, as the v0.9 user action in
`forwardedProps.a2uiAction.userAction`. To run code in the browser on a
click, see [Connect app state and actions](/generative-ui/components/state-and-actions).

## When should I use fixed schemas?

- The surface is well-known: flight cards, product tiles, order
  summaries, dashboards.
- You want deterministic, designer-controlled UI. No LLM schema drift.
- You want the fastest possible first paint; no secondary LLM call.

If the UI must adapt per prompt, reach for
**[dynamic schemas](./dynamic-schema)** instead.
