Use a dynamic schema when you cannot know the UI shape ahead of time,
for example a dashboard whose layout changes per question. Your agent
composes the surface (schema, data, and layout) from your components
on each turn.

## How it works

1. The agent calls the A2UI tool to draw a surface, made available
   when `injectA2UITool: true`.
2. The provider sends your client-side catalog (component names +
   prop schemas) to the agent as run context, so the LLM
   knows which components it may emit.
3. The tool call streams from the agent as `TOOL_CALL_ARGS` events.
4. The A2UI middleware intercepts the stream and renders cards
   progressively as data items arrive.

## The 3-file split

The canonical Bring-Your-Own-Catalog (BYOC) layout keeps three files
side by side in one folder, for example `app/a2ui/`:

| File | What lives there |
|---|---|
| `definitions.ts` | Zod props schema + a description for each custom component. Platform-agnostic, so the runtime can serialise it to the LLM. |
| `renderers.tsx` | React implementations keyed by the same names. TypeScript enforces that every definition has a renderer. |
| `catalog.ts` | `createCatalog(definitions, renderers, { includeBasicCatalog: true })`: merges your custom components with CopilotKit's built-in primitives. |

<Steps>
<Step>
### Install the packages

The definitions use Zod 3, and the example renderers use `recharts` and
`lucide-react`:

```npm
npm install @copilotkit/a2ui-renderer "zod@^3.25" recharts lucide-react
```

<Callout type="warn" title="A2UI catalogs need Zod 3">
  `@copilotkit/a2ui-renderer` converts Zod 3 schemas only. With Zod 4,
  TypeScript rejects the definitions, and every custom component reaches
  the model with empty props.
</Callout>
</Step>

<Step>
### Declare your custom component definitions

Each entry pairs a Zod prop schema with a description. The provider sends
each component's name and prop schema to the model. The `description`
field is not sent, so put usage guidance in the agent's instructions
(see [Tell the agent when to draw](#tell-the-agent-when-to-draw)). The
example below is a dashboard catalog with cards (`Card`, `StatusBadge`,
`Metric`, `InfoRow`, `DataTable`, `PrimaryButton`) and charts
(`PieChart`, `BarChart`). Save it as `app/a2ui/definitions.ts`:

At the end of the file, export the type that the renderers use:

```ts
export type MyDefinitions = typeof myDefinitions;
```

<Callout type="warn" title="Overriding Text, Row, or Column turns off data binding">
  This example overrides the basic `Text`, `Row`, and `Column` with
  plain-string props. Those versions do not accept `{ "path": ... }`
  bindings or repeating `children` templates, so the model's surface
  fails validation if it uses them. Leave these components out of your
  definitions if your agent binds data. To keep a binding, declare the
  prop as a union, for example
  `text: z.union([z.string(), z.object({ path: z.string() })])`.
</Callout>
</Step>

<Step>
### Implement the React renderers

Every key in `myDefinitions` must have a matching renderer. Props are
statically typed against the Zod schema, so refactors stay safe.
The demo renderers use the demo's own `Badge` and `Button` components,
its theme tokens, and `recharts` for the charts.

Start `app/a2ui/renderers.tsx` with the imports and helpers the renderers
use. Import your own `Badge` and `Button`, or use these plain stand-ins:

<Step>
### Pass the catalog to the provider

A single prop (`a2ui={{ catalog }}`) is all the frontend needs; the
provider registers the catalog and wires up the built-in A2UI
activity-message renderer. Add it to the provider from the
[quickstart](/quickstart):

```tsx title="app/providers.tsx"
"use client";

import { CopilotKitProvider } from "@copilotkit/react-core/v2";
import { myCatalog } from "./a2ui/catalog";

export function Providers({ children }: { children: React.ReactNode }) {
  return (
    <CopilotKitProvider
      runtimeUrl="/api/copilotkit"
      a2ui={{ catalog: myCatalog }} // [!code highlight]
    >
      {children}
    </CopilotKitProvider>
  );
}
```

That is all the default path needs. The catalog auto-enables A2UI and
injects the A2UI tool, so the runtime needs no `a2ui` block, unless your
agent brings its own A2UI tool (see [Agent setup](#agent-setup)). A
LangGraph agent with the CopilotKit middleware gets `generate_a2ui`.
Other agents get `render_a2ui`.
(No catalog? Turn it on from the runtime instead with
`a2ui: { injectA2UITool: true }`.)
</Step>

<Step>
### Tell the agent when to draw

A model with no instruction about the A2UI tool answers in prose and
never calls it. With the Built-in Agent, add a `prompt` in your runtime
route:

```ts title="app/api/copilotkit/[[...slug]]/route.ts"
const builtInAgent = new BuiltInAgent({
  model: "openai:gpt-6-luna",
  prompt:
    "When an answer needs a dashboard, a card layout, or a chart, call render_a2ui with components from the catalog.",
});
```

For other frameworks, see [Agent setup](#agent-setup).
</Step>

<Step>
### Ask for a dashboard

Ask the agent for a dashboard. For example, send `Show me my sales
dashboard for this quarter`. The dashboard renders in the chat with
cards, metrics, and charts from your catalog.
</Step>

## Agent setup

Tell the model in its instructions when to call the A2UI tool (`generate_a2ui` or
`render_a2ui`, as described above), for example for any answer that needs a
dashboard, a card layout, or a chart. A model with
no instruction about the tool answers in prose and never calls it.

## I opted out of auto-inject, now what?

When the runtime does not inject the A2UI tool, what you add
depends on your setup:

- **The runtime has an `a2ui` block, or the provider passes a catalog.**
  The runtime still attaches the `A2UIMiddleware`. Add only the A2UI
  agent tool below.
- **No catalog and no `a2ui` block.** A2UI is off. Add both the
  `A2UIMiddleware` and the A2UI agent tool below.

<Steps>
<Step>
### The `A2UIMiddleware`

The `A2UIMiddleware` is what turns the agent's `a2ui_operations` into
rendered surfaces. Without it, the agent's output never becomes UI; it
falls through as a plain tool result. The middleware can also add a
`render_a2ui` tool to the agent. To do this, set `injectA2UITool: true`
and skip the next step. Attach it to the AG-UI agent:

```typescript
import { A2UIMiddleware } from "@ag-ui/a2ui-middleware";

agent.use(new A2UIMiddleware({ injectA2UITool: false }));
```
</Step>

<Step>
### The A2UI agent tool

The `generate_a2ui` tool runs a secondary LLM (a subagent) that designs
the surface, which is why you hand it a model. With LangGraph Python,
build it with the AG-UI factory and add it to your agent's tools:

```python title="agent.py"
from ag_ui_langgraph import get_a2ui_tools
from langchain_openai import ChatOpenAI

generate_a2ui = get_a2ui_tools({
    "model": ChatOpenAI(model="gpt-6-luna", reasoning_effort="none"),
    "default_catalog_id": "declarative-gen-ui-catalog",  # the catalogId you pass to createCatalog
})

tools = [my_other_tool, generate_a2ui]
```

With other agents, define a `generate_a2ui` tool that calls a second
model and returns an `a2ui_operations` container. The
[Built-in Agent example](https://github.com/CopilotKit/CopilotKit/blob/main/showcase/integrations/built-in-agent/src/lib/factory/a2ui-factory.ts)
shows this in TypeScript.
</Step>
</Steps>

## Progressive streaming

The A2UI tool call (`render_a2ui`, or the subagent inside
`generate_a2ui`) streams from the agent as `TOOL_CALL_ARGS` events. The A2UI middleware:

1. Waits for the full `components` array before emitting anything;
   the schema must be complete before rendering starts.
2. Extracts `surfaceId` from the partial JSON.
3. Emits `createSurface` + `updateComponents` once the schema is
   complete.
4. Extracts complete `items` objects progressively and emits an
   `updateDataModel` for each, so cards appear one by one as data
   streams in.

A built-in progress indicator shows while the schema is still
generating and hides automatically once data items start arriving.

## When should I use dynamic schemas?

- You don't know the UI shape ahead of time; the agent decides what
  to show based on the user's request.
- You want to prototype A2UI without committing to a schema file yet.
- You're building a conversational dashboard where the layout varies
  per turn.

If the surface is well-known (for example, a product card or a flight result),
prefer a **[fixed schema](./fixed-schema)**. It's faster, cheaper,
and the UI is deterministic.
