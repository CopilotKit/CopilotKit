## What is this?

Frontend tools are browser functions that you register for the agent to call.
Their handlers run in the user's browser, so they can update component state,
use browser APIs, or call the UI libraries already used by the page. For
example, an agent can update React state, trigger an animation, read
`localStorage`, show a toast, or move the user's view.

This page covers the "agent drives the UI" shape of frontend tools. The same primitive also powers Generative UI and Human-in-the-loop; see those pages for interaction patterns.

## When should I use this?

Use a frontend tool when an agent needs the user's current browser context:
for example, to update React state, call a browser API, or show an app-owned
UI element such as a toast or chart. Keep server-side work in a backend tool.

Register a frontend tool with [`useFrontendTool`](/reference/hooks/useFrontendTool).
Give it a name, a Zod schema for parameters, and a handler. The agent can then
call it like any other tool and the browser runs the handler.

The handler receives the parsed, type-safe parameters and can do anything
the browser can: update state, call an API, touch the DOM. Its return value
is sent back to the agent as the tool result so the model can reason about
what happened.

## Await async work in a handler

A handler can return a promise. CopilotKit waits for it to settle, sends the
resolved value to the agent as the tool result, and then continues the run.
Use this when the agent needs data that only the browser can reach, such as a
client-side database, IndexedDB, or an API call made with the user's session.

<InlineDemo demo="frontend-tools-async" />

The `frontend-tools-async` cell registers a `query_notes` tool. Its handler
awaits a simulated 500 ms query against a local notes database and returns the
matching notes. The `render` function draws a notes card for the call. Until
the handler returns, `status` is not `"complete"` and the card shows its
loading state. After that, `result` holds the returned value as a JSON string,
which the cell parses before rendering the notes.

<Snippet cell="frontend-tools-async" region="frontend-tool-async-registration" title="frontend/src/app/demos/frontend-tools-async/page.tsx — async useFrontendTool" />

When the agent calls the tool, the handler's second argument carries a
`signal` that aborts when the run is stopped. Pass it to `fetch`, or check
`signal.aborted`, so slow work stops with the run.

To test it, ask the agent to find your notes about project planning. The card
shows its loading state for about half a second, then lists the matching
notes, and the agent's reply summarizes what the query returned.

## Registering a list of tools

`useFrontendTool` registers one tool per call, so it cannot be called in a loop
over a list whose length changes between renders. When the set of tools comes
from state, from props, or from a backend response, use
[`useFrontendTools`](/reference/hooks/useFrontendTools) instead. It takes an
array and runs a single effect over it, so the array can be empty on one render
and hold twenty entries on the next.

```tsx
useFrontendTools(
  reports.map((report) => ({
    name: `open_${report.id}`,
    description: `Open the ${report.title} report`,
    handler: async () => navigate(`/reports/${report.id}`),
  })),
  [navigate],
);
```

Tools that leave the array are unregistered, tools that join it are registered,
and a re-render that produces an equal list does not re-register anything. A
description built from your data stays current on its own. The second argument
is for values a handler closes over, such as `navigate` above.
