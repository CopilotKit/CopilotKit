## What is this?

MCP Apps are MCP servers that expose tools with associated UI resources. When the agent calls one of these tools, CopilotKit automatically fetches and renders the UI component in the chat. No additional frontend code is required.

Key benefits:
- **Zero frontend code**: UI components are served by the MCP server
- **Full interactivity**: Components can use HTML, CSS, and JavaScript
- **Secure sandboxing**: Content runs in isolated iframes
- **Thread persistence**: MCP Apps are stored in conversation history and restored on reconnect

## Implementation

<Steps>
  <Step>
    ### Install the middleware

    ```bash
    npm install @ag-ui/mcp-apps-middleware
    ```

    Use `@copilotkit/runtime` 1.76.0 or later. The current middleware release needs `@ag-ui/client` 1.x, which runtime 1.76.0 and later use.
  </Step>
  <Step>
    ### Add MCP Apps middleware to your agent

    Use `.use()` to attach the `MCPAppsMiddleware` to your `BuiltInAgent`:

    ```typescript title="app/api/copilotkit/[[...slug]]/route.ts" doctest="component"
    import {
      CopilotRuntime,
      createCopilotRuntimeHandler,
      InMemoryAgentRunner,
    } from "@copilotkit/runtime/v2";
    import { BuiltInAgent } from "@copilotkit/runtime/v2"; // [!code highlight]
    import { MCPAppsMiddleware } from "@ag-ui/mcp-apps-middleware"; // [!code highlight]

    const agent = new BuiltInAgent({
      model: "openai:gpt-6-luna",
      prompt: "You are a helpful assistant.",
    }).use( // [!code highlight:9]
      new MCPAppsMiddleware({
        mcpServers: [
          {
            type: "http",
            url: "https://mcp.excalidraw.com",
            serverId: "excalidraw",
          },
        ],
      }),
    );

    const runtime = new CopilotRuntime({
      agents: { default: agent },
      runner: new InMemoryAgentRunner(),
    });

    const handler = createCopilotRuntimeHandler({
      runtime,
      basePath: "/api/copilotkit",
    });

    export const GET = handler;
    export const POST = handler;
    ```

    <Callout type="info" title="Server ID">
      Always provide a `serverId` for production deployments. Without it, CopilotKit generates a hash from the server URL. If your URL changes (e.g., different environments), MCP Apps already stored in conversation history won't load correctly.
    </Callout>

    <Callout type="info" title="Using Intelligence?">
      On a runtime connected to Intelligence, configure the servers with the runtime's `mcpApps` option instead, and pass `intelligence` in place of `runner`. See [MCP Apps with Intelligence](#mcp-apps-with-intelligence).
    </Callout>
  </Step>
  <Step>
    ### Give it a try

    Ask the agent to draw a flowchart of a login flow with Excalidraw. The Excalidraw widget renders in the chat. No changes to your frontend are needed.
  </Step>
</Steps>

## MCP Apps with Intelligence

On a runtime connected to [Intelligence](/intelligence/quickstart), configure the MCP servers with the runtime's `mcpApps` option. On every run, the runtime attaches the MCP Apps middleware to the agent. Intelligence stores the threads and runs, so the MCP Apps in a conversation are restored when the thread is loaded.

Move the server list from `MCPAppsMiddleware` to `mcpApps`. Then remove `runner`, and add `intelligence` and `identifyUser`:

```typescript title="app/api/copilotkit/[[...slug]]/route.ts"
import {
  BuiltInAgent,
  CopilotKitIntelligence,
  CopilotRuntime,
  createCopilotRuntimeHandler,
} from "@copilotkit/runtime/v2";

const agent = new BuiltInAgent({
  model: "openai:gpt-6-luna",
  prompt: "You are a helpful assistant.",
});

const runtime = new CopilotRuntime({
  agents: { default: agent },
  // Intelligence stores threads and runs. Do not pass `runner` as well.
  intelligence: new CopilotKitIntelligence({
    apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
  }),
  // Replace this fixed user with the user from your verified session.
  identifyUser: () => ({ id: "demo-user", name: "Demo User" }),
  mcpApps: {
    servers: [
      {
        type: "http",
        url: "https://mcp.excalidraw.com",
        serverId: "excalidraw",
      },
    ],
  },
});

const handler = createCopilotRuntimeHandler({
  runtime,
  basePath: "/api/copilotkit",
});

export const GET = handler;
export const POST = handler;
export const PATCH = handler;
export const DELETE = handler;
```

Keep the same `serverId` values when you move to Intelligence. The stored MCP Apps in a thread refer to the server by that ID.

To give a server to one agent only, add `agentId` to its entry in `mcpApps.servers`.

For the API key, user identity, and route protection, follow the [Intelligence quickstart](/intelligence/quickstart).

## Sandbox and widget storage

Each MCP App runs in a sandboxed iframe with an opaque origin. A widget cannot read the cookies, storage, or DOM of your page. It cannot read responses from your APIs either, unless an API allows cross-origin requests (for example with `Access-Control-Allow-Origin: *`). It can still send requests, so protect state-changing endpoints against cross-site request forgery, as for any other site. As a result, the widget also cannot use `localStorage`, `sessionStorage`, `IndexedDB`, or cookies of its own.

Requests from a widget that need CORS, such as `<script type="module">` and `fetch`, are sent with `Origin: null`. Serve public widget assets with `Access-Control-Allow-Origin: *`. Classic `<script src>` tags do not need CORS. To avoid CORS, bundle the widget into a single HTML file, as the [ext-apps examples](https://github.com/modelcontextprotocol/ext-apps/tree/main/examples) do with `vite-plugin-singlefile`.

The MCP Apps spec pairs `allow-same-origin` with a sandbox served from a separate origin. CopilotKit loads the sandbox inline, so it leaves `allow-same-origin` off. With that flag on an inline sandbox, a widget gets the origin of your page.

If you wrote a widget yourself and it needs storage, you can restore `allow-same-origin`:

```tsx
<CopilotKit runtimeUrl="/api/copilotkit" mcpApps={{ allowSameOriginFallback: true }}>
  {children}
</CopilotKit>
```

<Callout type="warn" title="Only for widgets you trust">
  With `allowSameOriginFallback`, every MCP App runs with the origin of your page. The widget of any connected MCP server can then read your cookies and storage and act as the signed-in user. Do not enable it if you connect third-party MCP servers.
</Callout>

## Transport Types

The middleware supports two transport types:

### HTTP Transport

For MCP servers using HTTP-based communication:

```typescript
{
  type: "http",
  url: "http://localhost:3101/mcp",
  serverId: "my-http-server"
}
```

### SSE Transport

For MCP servers using Server-Sent Events:

```typescript
{
  type: "sse",
  url: "https://mcp.example.com/sse",
  headers: {
    "Authorization": "Bearer token"
  },
  serverId: "my-sse-server"
}
```
