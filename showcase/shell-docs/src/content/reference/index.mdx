The CopilotKit 2.0 React API (`@copilotkit/react-core`) gives you hooks and components for apps that talk to agents over the [AG-UI](https://docs.ag-ui.com) protocol.

## Provider Setup

Wrap your application with `<CopilotKitProvider>` to configure the runtime connection:

```tsx
import { CopilotKitProvider } from "@copilotkit/react-core";
import type { ReactNode } from "react";

export function Providers({ children }: { children: ReactNode }) {
  return (
    <CopilotKitProvider runtimeUrl="/api/copilotkit" agentId="default">
      {children}
    </CopilotKitProvider>
  );
}
```

`<CopilotKitProvider>` is the 2.0 provider. `<CopilotKit>` is still exported as an alias of it, with the same props. Name the agent with `agentId` (v1 used `agent`). See [Migrate to 2.0](/migrate/v2).

### Props

<PropertyReference name="agentId" type="string" default='"default"'>
  Default agent for chats and hooks under this provider. An explicit hook or
  chat `agentId`, or a surrounding chat configuration, takes precedence.
</PropertyReference>

<PropertyReference name="licenseToken" type="string">
  Signed license token for offline verification of CopilotKit Intelligence features.
</PropertyReference>

<PropertyReference name="selfManagedAgents" type="Record<string, AbstractAgent>">
  AG-UI agents managed by your app and registered directly with CopilotKit.
  Use this when you connect to agents without routing through a Copilot Runtime.
</PropertyReference>

<PropertyReference name="openGenerativeUI" type="{ sandboxFunctions?: SandboxFunction[]; designSkill?: string }">
  Configuration for Open Generative UI. Use `sandboxFunctions` to expose host
  functions to generated sandboxed iframes, and `designSkill` to override the
  design guidance injected as agent context for `generateSandboxedUi`.
</PropertyReference>

<PropertyReference name="defaultThrottleMs" type="number">
  Default throttle interval, in milliseconds, for `useAgent` re-renders caused
  by message and state updates. Individual `useAgent` calls and prebuilt chat
  components can override it with their own `throttleMs`.
</PropertyReference>

<PropertyReference name="debug" type="DebugConfig">
  Enable client-side debug logging for the AG-UI transport and event pipeline.
  Pass `true` for event and lifecycle summaries, or a config object with
  `verbose: true` to include full event payloads.
</PropertyReference>

<PropertyReference name="runtimeUrl" type="string">
  URL of the CopilotKit runtime endpoint. Lazily forwarded to the core after
  mount.
</PropertyReference>

<PropertyReference name="headers" type="Record<string, string> | (() => Record<string, string>) | (() => Promise<Record<string, string>>)" default="{}">
  Request headers forwarded with runtime calls. Pass an object for static
  headers, or a function (sync or async) to build them fresh. A builder runs
  when each request is sent, so a refreshed token is always used. An inline
  arrow is fine.

  Cache inside the builder. Clerk's and Auth0's `getToken()` already cache. A
  builder that calls the network every time adds one call per request.

  If the builder throws or rejects, that request is not sent and `onError`
  gets `header_resolution_failed`.

  Re-passing the same builder function is a no-op. On a user switch, remount
  the provider (e.g. `key={userId}`), so Inspector metadata and thread lists
  reload for the new user. This does not refetch the runtime's `/info`.

  `copilotkit.headers` is the last resolved value. Use
  `await copilotkit.resolveHeaders()` for your own requests.

  Core headers are also sent to any `selfManagedAgents` /
  `agents__unsafe_dev_only` agent, including ones on other origins. Don't put
  a bearer token in core headers if those agents point at a third party.

  ```tsx
  import { CopilotKitProvider } from "@copilotkit/react-core";
  import type { ReactNode } from "react";
  import { useAuth } from "./auth";

  export function Providers({ children }: { children: ReactNode }) {
    const { getToken } = useAuth();

    return (
      <CopilotKitProvider
        runtimeUrl="/api/copilotkit"
        headers={async () => ({ Authorization: `Bearer ${await getToken()}` })}
      >
        {children}
      </CopilotKitProvider>
    );
  }
  ```
</PropertyReference>

<PropertyReference name="credentials" type="RequestCredentials">
  Credentials mode for fetch requests (e.g. `"include"` for HTTP-only cookies in
  cross-origin requests).
</PropertyReference>

<PropertyReference name="messageFilter" type="CopilotKitMessageFilter">
  Rewrites the message list sent to runtime agents on every run:
  `(messages, { agentId }) => Message[]`. The filter changes the request body
  only; the transcript the UI renders is untouched, and broken tool-call pairs
  are repaired before the request is sent. Agents your app passes in directly,
  Intelligence runs, and suggestion runs are not filtered. Prefer a stable
  reference (`useCallback`).
</PropertyReference>

<PropertyReference name="publicApiKey" type="string">
  Copilot Cloud public API key.
</PropertyReference>

<PropertyReference name="publicLicenseKey" type="string">
  Alias for `publicApiKey`.
</PropertyReference>

<PropertyReference
  name="properties"
  type="Record<string, unknown>"
  default="{}"
>
  Runtime metadata payload.
</PropertyReference>

<PropertyReference name="useSingleEndpoint" type="boolean">
  When omitted, transport is negotiated from the runtime info response. Set
  `true` to use a single endpoint or `false` to use separate routes.
</PropertyReference>

<PropertyReference
  name="agents__unsafe_dev_only"
  type="Record<string, AbstractAgent>"
>
  Preinstantiated agents for development/testing. **Not intended for production
  use.**
</PropertyReference>

<PropertyReference name="renderToolCalls" type="ReactToolCallRenderer[]">
  Static set of tool call renderers. The array should be stable across renders.
</PropertyReference>

<PropertyReference
  name="renderActivityMessages"
  type="ReactActivityMessageRenderer[]"
>
  Static set of activity message renderers.
</PropertyReference>

<PropertyReference
  name="renderCustomMessages"
  type="ReactCustomMessageRenderer[]"
>
  Static set of custom message renderers.
</PropertyReference>

<PropertyReference name="markdownRenderer" type="MarkdownRenderer">
  Global markdown renderer for assistant and reasoning messages: a config
  object for the built-in renderer (`DefaultMarkdownRendererProps`) or a
  component that takes `MarkdownRendererProps`. A per-message
  `markdownRenderer` slot still wins. See
  [`@copilotkit/markdown`](/reference/packages/markdown).
</PropertyReference>

<PropertyReference name="frontendTools" type="ReactFrontendTool[]">
  Static tool handlers defined at the provider level. The array should be stable
  across renders.
</PropertyReference>

<PropertyReference name="humanInTheLoop" type="ReactHumanInTheLoop[]">
  Declarative human-in-the-loop tool definitions. Each becomes both a tool
  handler and a tool call renderer.
</PropertyReference>

<PropertyReference name="messageFilter" type="(messages: Message[], context: { agentId: string }) => Message[]">
  Rewrites the message list sent to runtime agents on every run. Return the
  messages to send. The transcript that the UI renders does not change.
  Intelligence runs and suggestion runs are not filtered. Pass a stable
  reference (`useCallback`).
</PropertyReference>

<PropertyReference name="showIntelligenceIndicator" type="boolean" default="true">
  Whether to mount the Intelligence indicator in chat automatically.
</PropertyReference>

<PropertyReference name="generativeUI" type="GenerativeUIConfig">
  Native generative UI: pass `{ ui }`, where `ui` comes from
  `createGenerativeUI`. The agent renders your React components into chat or
  into `<GenerativeUISurface id>` mounts. When you leave it out and the runtime
  has generative UI on, the provider uses the standard catalog.
</PropertyReference>

<PropertyReference name="mcpApps" type="{ allowSameOriginFallback?: boolean }">
  Options for the built-in MCP Apps renderer. `allowSameOriginFallback`
  (default `false`) restores `allow-same-origin` on the MCP App sandbox. The
  widget then runs with the origin of your page, so set it only for widgets
  that you wrote and trust.
</PropertyReference>

<PropertyReference name="learning" type="boolean | LearningConfig & { autoStart?; trajectoryId?; learningContainerIds? }">
  Turns on interaction capture (`@copilotkit/learning`). Pass `true` for the
  default options, or an object for options such as `autoStart` and
  `trajectoryId`. Omit the prop or pass `false` to turn capture off. Capture
  starts after mount unless `autoStart` is `false`, and stops on unmount. Read
  the active ID from `copilotkit.trajectoryId`.
</PropertyReference>

<PropertyReference name="enableInspector" type="boolean">
  Controls the CopilotKit Inspector in development browser builds on localhost
  or loopback hosts. It is shown by default unless set to `false`, and is never
  loaded on remote hosts, in production, or during SSR, even when explicitly
  set to `true`.

  2.0 removed the `showDevConsole` prop and its error banners. Runtime, agent,
  and tool errors show in the Inspector. To handle them in your code, use
  `onError`.
</PropertyReference>

<PropertyReference name="onError" type="(event: { error: Error; code: CopilotKitCoreErrorCode; context: Record<string, any> }) => void | Promise<void>">
  Error handler called when CopilotKit encounters an error. Fires for all error types: runtime connection failures, agent errors, and tool errors.

`onError` works with any configuration. It does not need a `publicApiKey`.

```tsx
import { CopilotKitProvider } from "@copilotkit/react-core";
import type { ReactNode } from "react";

export function Providers({ children }: { children: ReactNode }) {
  return (
    <CopilotKitProvider
      runtimeUrl="/api/copilotkit"
      onError={(event) => {
        console.error(`[${event.code}]`, event.error.message, event.context);
      }}
    >
      {children}
    </CopilotKitProvider>
  );
}
```

</PropertyReference>

## Import Surfaces

Use the main entry when your app renders CopilotKit's web UI components or generative UI surfaces:

```tsx
import {
  CopilotKitProvider,
  CopilotChat,
  useAgent,
} from "@copilotkit/react-core";
```

Use the headless entry when you build a fully custom chat surface and only need platform-agnostic hooks. This avoids the built-in chat rendering stack and its CSS:

```tsx
import {
  useAgent,
  useCopilotKit,
  useFrontendTool,
  useRenderToolCall,
} from "@copilotkit/react-core/headless";
```

The headless entry exports the provider context, chat configuration provider, `useAgent`, tool hooks, suggestions, threads, capabilities, and shared types. It does not export `CopilotKitProvider`, `CopilotChat`, `CopilotPopup`, `CopilotSidebar`, `useDefaultRenderTool`, or generative UI render helpers.

## Styling

The UI components include their own styles. You don't import a stylesheet. `CopilotChat`, `CopilotPopup`, and `CopilotSidebar` add one `<style>` tag to the page, and it is included in server-rendered HTML.

If you render other components without a chat surface, add `<CopilotKitStyles />` once, inside `CopilotKitProvider`. If your Content-Security-Policy limits `style-src` to a nonce, pass it as `<CopilotKitProvider nonce={nonce}>`.

### Load the CSS as a cached file

The `<style>` tag is part of your JavaScript, so browsers cache it with your app's code. Server-rendered pages also send it in the HTML of each full page load. To have browsers cache the CSS as its own file, import it and turn off the `<style>` tag:

```tsx
import type { ReactNode } from "react";
import { CopilotKitProvider } from "@copilotkit/react-core";
import "@copilotkit/core/styles.css";

export function Providers({ children }: { children: ReactNode }) {
  return (
    <CopilotKitProvider runtimeUrl="/api/copilotkit" injectStyles={false}>
      {children}
    </CopilotKitProvider>
  );
}
```

This is optional. Your bundler must support CSS imports, as Next.js and Vite do.

To update an app that still imports `@copilotkit/react-core/v2/styles.css`, run the codemod in [Migrate to v2](/migrate/v2#remove-the-stylesheet-import).
