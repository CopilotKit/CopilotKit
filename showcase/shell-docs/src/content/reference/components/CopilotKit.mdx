<Callout type="info" title="This is the v1 provider, re-exported for back-compat">
  `<CopilotKit>` is the v1 provider. It is re-exported from
  `@copilotkit/react-core/v2` so that a v1 application keeps working after the
  import path changes, and it renders `<CopilotKitProvider>` internally. **The
  v2 provider is `<CopilotKitProvider>`** — reach for that one in new v2 code.
</Callout>

The two are not aliases: they name the agent with different props.

|                | v1 `<CopilotKit>`  | v2 `<CopilotKitProvider>` |
| -------------- | ------------------ | ------------------------- |
| Name the agent | `agent="my_agent"` | `agentId="my_agent"`      |

You can also name the agent per chat with `<CopilotChat agentId="my_agent">`, or
for a subtree with `<CopilotChatConfigurationProvider agentId="my_agent">`. Both
of those override the provider-level default. See [Provider and handler
pairs](/backend/runtime-endpoints#provider-and-handler-pairs).

Both providers treat an omitted `useSingleEndpoint` the same way: the transport
is negotiated from the Runtime info response. Versions before 1.70.2 pinned
`<CopilotKit>` to the single-route transport.

This component will typically wrap your entire application (or a sub-tree of your application where you want to have a copilot). It provides the copilot context to all other components and hooks.

## Example

You can find more information about self-hosting CopilotKit [here](/direct-to-llm/guides/self-hosting).

```tsx
import { CopilotKit } from "@copilotkit/react-core/v2";

<CopilotKit runtimeUrl="<your-runtime-url>">// ... your app ...</CopilotKit>;
```

## Browser Autopilot (prototype)

The `autopilot` option on `CopilotKitProvider` can install CopilotKit's browser tools.
Runtime-side Autopilot activation is also required. Scope configuration alone narrows
execution; supply an `adapter` to install the browser integration.

```tsx
<CopilotKitProvider
  runtimeUrl="/api/copilotkit"
  autopilot={{
    agents: ["assistant"],
    adapter: {
      identity: { userId: user.id, organizationId: user.organizationId },
      canWrite: validateCurrentSession,
      navigation: {
        push: (path) => router.push(path),
        allowedPath: isAllowedAppPath,
        mayLeave: confirmLeavingUnsavedChanges,
      },
    },
  }}
>
  <Application />
  <CopilotSidebar />
</CopilotKitProvider>
```

Keep the adapter stable with `useMemo`. `canWrite` must revalidate the current
server session; this browser check never replaces server authorization.
CopilotKit registers discovery, navigation, search, clarification, form submission,
and control activation. Do not register those tools manually or add generic model
instructions in your application. All reads share a request budget. Reviewed writes
hold a browser record lock until completion or an uncertain outcome.

The adapter contains application policy, not agent actions. Write targets still
need stable record/draft identity and version annotations. Normal application
handlers report their server result through `performBrowserAction`:

```tsx
import { performBrowserAction } from "@copilotkit/react-core/v2";

async function onSubmit(event) {
  event.preventDefault();
  const form = event.currentTarget;
  await performBrowserAction(form, event.nativeEvent, async () => {
    const result = await saveUsingExistingAppHandler(new FormData(form));
    return { status: "completed", recordId: result.id, version: result.version };
  });
}
```

Return `failed` only after a definitive server rejection, and `uncertain` when the
write may have reached the server. A DOM click alone is not proof of completion.
An optional fourth argument supplies normal manual confirmation; an approved
Autopilot dispatch reuses its review rather than asking twice.

Forms expose `data-autopilot-record-id`, `data-autopilot-record-version`, and
`data-autopilot-handler-version`; new forms use `data-autopilot-draft-id` instead
of record identity. Buttons additionally declare `data-copilot-action` and can
provide `data-copilot-confirm` as their review text. Use `data-copilot-private` on
excluded regions and `data-copilot-page` on the readable app root. GET search forms
must explicitly declare `data-copilot-readonly-form`. These are supported prototype
contracts, not automatic support for arbitrary widgets or business applications.

Built-in chat uses the provider's approval and clarification controllers by default.
For a custom/headless surface, pass stable `approvalController` and
`clarificationController` instances in `autopilot`, then consume them through
`useCopilotApproval`, `useCopilotApprovalWork`, and `useCopilotClarification` from
`@copilotkit/react-core/v2/headless`. A real trusted user event is required to respond.
