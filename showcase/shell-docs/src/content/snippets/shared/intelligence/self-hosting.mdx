## What is this?

CopilotKit Intelligence — the platform that powers threads, shared state, and the inspector — can be self-hosted on your own Kubernetes cluster using the `copilot-intelligence` Helm chart. You run the control plane and data plane inside your own network boundary; the chart leaves you in charge of identity, storage, and secrets.

**What you bring:**

- Postgres and Redis — your own, or the bundled Bitnami subcharts
- An OIDC provider for identity
- Secrets via External Secrets Operator, direct Kubernetes Secrets, or chart-managed credentials

**What the chart deploys:**

| Component                       | Role                                | Port |
| ------------------------------- | ----------------------------------- | ---- |
| `app-api`                       | Backend service                     | 4201 |
| `app-frontend`                  | Web UI                              | 8080 |
| `realtime-gateway` | WebSocket service for realtime sync (enabled by default) | 4401 |
| `embeddings` | In-cluster text embeddings for Memories; omitted when an external provider is configured | 80 |

Optional jobs apply product and Analytics database migrations, bootstrap organization access, and run the thread culler. The chart also includes the usual supporting resources (Services, Ingress, HPAs, PodDisruptionBudgets, ConfigMaps, and — when ESO is enabled — ExternalSecret resources).

## When should I use this?

- Your organization requires CopilotKit Intelligence to run inside your own VPC or data center for compliance, data residency, or security reasons
- You want to connect CopilotKit Intelligence to internal databases, identity providers, or secret stores that are not reachable from the cloud-hosted version
- You need to operate the platform under your existing Kubernetes tooling, CI/CD, and monitoring stack
- You have a CopilotKit Intelligence license and the platform-engineering capacity to run a production Kubernetes workload

<Callout type="info" title="Validate locally before committing to a real cluster">
Use the `values-quickstart-local.yaml` overlay included in the downloaded chart for bundled PostgreSQL and Redis. Add the [local evaluation overlay](#local-evaluation-overlay) below to enable ingress and supply your own OIDC configuration and deployment license. This path uses only the released chart and Kubernetes tooling.
</Callout>

## Prerequisites

Before starting, make sure the following are in place. [CopilotKit Intelligence architecture](/intelligence/intelligence-platform) explains the application/runtime/platform layers in more depth.

**License and registry access:**

- A valid CopilotKit Intelligence license key (contact your CopilotKit account team if you do not have one)
- Read access to the chart OCI registry at `oci://ghcr.io/copilotkit/charts/intelligence` (anonymous pulls are allowed for the released chart)
- A released chart version. Run `helm show chart oci://ghcr.io/copilotkit/charts/intelligence` to inspect the latest published chart, then use its `version` value for the `<chart-version>` placeholder throughout this guide. Pin that version for repeatable installs.

**Cluster and tooling:**

- Kubernetes ≥ 1.28
- Helm ≥ 3.12
- `kubectl` configured against the target cluster with an admin-equivalent context

**Platform prerequisites (cluster-wide, installed once):**

- An ingress controller — either `nginx-ingress` or the AWS Load Balancer Controller
- `cert-manager` (or a cloud-managed certificate alternative such as AWS ACM) for TLS on the public hostnames
- `External Secrets Operator` if you plan to sync secrets from AWS Secrets Manager, HashiCorp Vault, or GCP Secret Manager (recommended for production, but not required — see [Secrets](#create-secrets))

**External dependencies (reachable from the cluster):**

- PostgreSQL ≥ 14 with pgvector ≥ 0.8.0 available — migrations use the `vector` extension and `halfvec` type for Memories. The bundled evaluation database includes pgvector; an external database must provide it before migrations run.
- Redis ≥ 7 (or a Valkey-compatible service such as Amazon ElastiCache)
- An OIDC identity provider — Keycloak, Okta, Azure AD, Auth0, Google Workspace, or equivalent. Its issuer URL must be reachable from both the browser and the cluster; register the application origin and callback URL with the provider.

**Optional:**

- TimescaleDB for [Analytics](#analytics-optional), with separate runtime and schema-owner credentials
- An S3-compatible object store for configured object-storage features, including Channel files

## Implementation

<Steps>
  <Step>
    ### Prepare your Kubernetes cluster

    Ensure `kubectl` points to the cluster that will run CopilotKit Intelligence.

    ```bash title="Terminal"
    kubectl config current-context
    kubectl auth can-i create namespace --all-namespaces
    ```

    Confirm the context names your target cluster and that the permission check returns `yes`. If not, fix your kubeconfig before proceeding.

  </Step>

  <Step>
    ### Install platform prerequisites

    These components are cluster-wide and installed once per cluster, independently of the application chart.

    <Tabs items={["AWS (EKS)", "On-prem / generic", "Local (Docker Desktop / k3d)"]}>
      <Tab value="AWS (EKS)">
        ```bash title="Terminal"
        # AWS Load Balancer Controller (kube-system)
        helm repo add eks https://aws.github.io/eks-charts
        helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
          -n kube-system \
          --set clusterName=<YOUR_CLUSTER_NAME>

        # cert-manager
        helm repo add jetstack https://charts.jetstack.io
        helm install cert-manager jetstack/cert-manager \
          -n cert-manager --create-namespace \
          --set installCRDs=true

        # External Secrets Operator (optional — see Secrets step)
        helm repo add external-secrets https://charts.external-secrets.io
        helm install external-secrets external-secrets/external-secrets \
          -n external-secrets --create-namespace
        ```
      </Tab>
      <Tab value="On-prem / generic">
        ```bash title="Terminal"
        # NGINX Ingress Controller
        helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
        helm install ingress-nginx ingress-nginx/ingress-nginx \
          -n ingress-nginx --create-namespace

        # cert-manager
        helm repo add jetstack https://charts.jetstack.io
        helm install cert-manager jetstack/cert-manager \
          -n cert-manager --create-namespace \
          --set installCRDs=true
        ```
      </Tab>
      <Tab value="Local (Docker Desktop / k3d)">
        ```bash title="Terminal"
        # NGINX Ingress Controller as ClusterIP — you will reach it via
        # `kubectl port-forward` later, so no LoadBalancer service is needed.
        helm upgrade --install ingress-nginx ingress-nginx \

          --namespace ingress-nginx --create-namespace \

        ```

      </Tab>
    </Tabs>

    After each controller is running, its pods should be `Ready` in their respective namespaces.

  </Step>

  <Step>
    ### Provision external dependencies

    Intelligence needs Postgres, Redis, and an OIDC issuer. You can either point the chart at managed services you already run, or enable the bundled Bitnami subcharts for in-cluster Postgres and Redis (appropriate for evaluation and small self-hosted installs).

    **Using managed services (recommended for production):**

    - Create a Postgres database and user. Record the host, port (default `5432`), database name, username, and password.
    - Create a Redis instance with TLS enabled. Record the host, port (default `6379`), and password.
    - Configure an OIDC client in your identity provider. Record the issuer URL, client ID, and client secret.

    **Using the bundled in-cluster subcharts:**

    Set `postgresql.enabled: true` and `redis-subchart.enabled: true` in your values file (covered in the next step). A matching `StorageClass` must exist in the cluster. For the public chart-only evaluation flow below, keep `keycloak.enabled: false` and use an OIDC issuer reachable from both your browser and cluster. The [bundled Keycloak subchart](#bundled-keycloak-eval-only) requires additional hostname and exposure configuration before browser login works.

    The chart ships `values-quickstart-local.yaml` with bundled Postgres + Redis, `migrations.enabled: true`, and resources sized for evaluation. Its auth defaults expect repository-local services. Layer the local evaluation overlay below on top to configure your own OIDC issuer, credentials, license, and ingress.

  </Step>

  <Step>
    ### Create a values file

    The released chart ships several example values files for the common deployment shapes. Pick the one closest to your environment and copy it into a working overlay you can edit. Pull and untar the chart so you have local copies to diff against:

    ```bash title="Terminal"
    helm pull oci://ghcr.io/copilotkit/charts/intelligence --version <chart-version> --untar

    # AWS-flavored (ALB, IRSA, External Secrets from AWS Secrets Manager)
    cp intelligence/values-aws-example.yaml my-values.yaml

    # Or on-prem-flavored (nginx, manual Kubernetes Secrets)
    cp intelligence/values-onprem-example.yaml my-values.yaml

    # For local evaluation, use the my-values.yaml overlay below instead.
    ```

    The chart untars into a directory named `intelligence/` (the published chart name on GHCR; the chart's `nameOverride` keeps release-prefixed resources named `cpki-*`).

    Edit `my-values.yaml` to set at minimum:

    - `database.host`, `database.port`, `database.name` — your Postgres connection (`name` defaults to `intelligence`)
    - `redis.host`, `redis.port`, `redis.tls` — your Redis connection (TLS is on by default; managed Redis requires it)
    - `auth.deploymentMode: self_hosted` and `auth.issuer` — your OIDC deployment mode and issuer URL
    - `auth.existingSecret` — name of the Kubernetes Secret containing `auth-secret`, `auth-client-id`, `auth-client-secret` (or use one of the alternate paths in [Secrets](#create-secrets))
    - `ingress.ui.host` — the hostname users will load the Intelligence UI on (for example `intelligence.example.com`)
    - `ingress.api.host` — optional dedicated API hostname. When omitted, the `ui.host` rule routes `/api` and `/auth` paths to `app-api`, so a single hostname is fine for most installs.
    - `ingress.realtimePlane.host` — the hostname for the enabled realtime gateway (for example `realtime.intelligence.example.com`); include it in your TLS configuration
    - `config.appFrontendOrigin` — the public browser origin, such as `https://intelligence.example.com`, for authenticated bootstrap writes
    - `ingress.tls` — TLS configuration for the hosts above
    - `migrations.enabled: true` — **required for first install**; defaults to `false`. Without it the database schema is never applied and `app-api` will crashloop. (The eval overlay `values-quickstart-local.yaml` sets this for you when you layer on top of it.)

    <Callout type="warn" title="OIDC issuer URL — trailing slash matters">
      Some providers (Auth0 in particular) only accept the issuer URL with a trailing slash (e.g. `https://your-tenant.auth0.com/`). A missing or extra slash produces an opaque "issuer mismatch" failure at login time. Match the value exactly to what your provider's discovery endpoint advertises.
    </Callout>

    Configure initial organization access with the additive bootstrap Job. Match the claim names and values your OIDC provider actually sends:

    ```yaml title="my-values.yaml"
    bootstrap:
      enabled: true
      organizations:
        - slug: acme
          name: Acme Corporation
          mappings:
            - role: org_member
              claimName: groups
              claimValue: acme-intelligence-users
      platformAdminMappings:
        - claimName: groups
          claimValue: intelligence-platform-admins
    ```

    The Job runs after product migrations and can be rerun without duplicating existing mappings. Organization membership and deployment-wide platform-admin access are separate grants. OIDC login alone does not assign either role.

    Memories use the chart's default embeddings service. It requests 2 GiB of memory and a 5 GiB model-cache volume. To use an external OpenAI-compatible provider instead, configure `embeddings.external.url` and `embeddings.external.model`, plus `embeddings.external.apiKey.existingSecret` and `secretKey` when authentication is required. Its output must match the 1024-dimensional storage schema; `embeddings.external.dimensions` defaults to `1024`.

    <h4 id="local-evaluation-overlay">Local evaluation overlay</h4>

    For local evaluation, use the following as `my-values.yaml` on top of `values-quickstart-local.yaml`. Keep the bundled database and Redis settings from that file; do not add the external database Secret overrides. Create the **auth**, **gateway**, **BEAM cookie**, and **deployment-license** Secrets described in Path B below, using your OIDC client's actual credentials. Add the bootstrap mappings above for the identities your provider sends.

    ```yaml title="my-values.yaml"
    keycloak:
      enabled: false
    localDevSecrets:
      enabled: false
    auth:
      issuer: https://your-oidc-provider.example.com
      existingSecret: cpki-auth
    appApi:
      service:
        type: ClusterIP
      licenseSecret:
        existingSecret: cpki-deployment-license
        key: license-token
    appFrontend:
      service:
        type: ClusterIP
    realtimeGateway:
      existingSecret: cpki-realtime-gateway
      beam:
        cookieSecret:
          name: cpki-beam-cookie
      service:
        type: ClusterIP
    ingress:
      enabled: true
      className: nginx
      ui:
        host: localhost
      api:
        host: ""
      realtimePlane:
        host: ""
      tls: []
    config:
      appFrontendOrigin: http://localhost:8080
      publicAppOrigin: http://localhost:8080
    ```

    The local base overlay disables ingress and assumes a separately provisioned local identity provider. These overrides enable ingress, replace that issuer, and use your real auth and license Secrets. The issuer must resolve to the same OIDC service from both your browser and the cluster. Configure its allowed callback URL for `http://localhost:8080/auth/callback/enterprise-sso` (or your configured `auth.providerId`). If your provider disallows HTTP localhost callbacks, use a reachable HTTPS hostname and TLS instead.

    See the [Configuration reference](#configuration-reference) section for the full set of values.

  </Step>

  <Step id="create-secrets">
    ### Create secrets

    The chart supports three paths for secrets management. Pick exactly one. Every self-hosted deployment also needs the issued deployment license token. Helm never generates this token; it is separate from a project API key and does not require enabling the thread culler.

    **Path A — External Secrets Operator (recommended for production):**

    1. Ensure your secret backend (AWS Secrets Manager, Vault, etc.) has entries for the database URL, Redis URL, auth credentials, realtime gateway secrets, and BEAM clustering cookie.
    2. Create a `ClusterSecretStore` (or `SecretStore`) that references that backend.
    3. In `my-values.yaml`, set `externalSecrets.enabled: true`, `externalSecrets.store.kind`, and `externalSecrets.store.name` to match. Enable the gateway and BEAM cookie mappings under `externalSecrets.secrets.realtimeGateway.enabled` and `externalSecrets.secrets.beamCookie.enabled`.
    4. Store the issued license in your secret backend and enable its mapping:

    ```yaml title="my-values.yaml"
    externalSecrets:
      enabled: true
      store:
        name: your-secret-store
      secrets:
        realtimeGateway:
          enabled: true
        beamCookie:
          enabled: true
        license:
          enabled: true
          remoteRef: copilot-intelligence/license
          target: cpki-license
          properties:
            - remoteKey: licenseToken
              secretKey: license-token
    ```

    Adjust `remoteRef` and `remoteKey` to the entry containing your issued token. The chart then injects the synchronized license into App API automatically.

    **Path B — Direct Kubernetes Secrets (you manage the rotations):**

    Leave `externalSecrets.enabled: false` (the default) and create the Secrets manually before installing:

    ```bash title="Terminal"
    kubectl create namespace copilot-intelligence

    kubectl create secret generic cpki-db \
      --from-literal=database-url='postgresql://user:pass@host:5432/intelligence' \
      -n copilot-intelligence

    kubectl create secret generic cpki-redis \
      --from-literal=redis-url='rediss://:password@host:6379' \
      -n copilot-intelligence

    kubectl create secret generic cpki-auth \
      --from-literal=auth-secret="$(openssl rand -hex 32)" \
      --from-literal=auth-client-id='<OIDC client id>' \
      --from-literal=auth-client-secret='<OIDC client secret>' \
      -n copilot-intelligence
    ```

    The realtime gateway is enabled by default. Create its credentials and the cookie used by default BEAM clustering:

    ```bash title="Terminal"
    kubectl create secret generic cpki-realtime-gateway \
      --from-literal=runner-auth-secret="$(openssl rand -hex 32)" \
      --from-literal=secret-key-base="$(openssl rand -base64 96 | tr -d '\n')" \
      -n copilot-intelligence

    kubectl create secret generic cpki-beam-cookie \
      --from-literal=release-cookie="$(openssl rand -hex 32)" \
      -n copilot-intelligence
    ```

    Create the deployment-license Secret from a local file containing the issued token:

    ```bash title="Terminal"
    kubectl create secret generic cpki-deployment-license \
      --from-file=license-token=/secure/path/copilotkit-license-token \
      -n copilot-intelligence
    ```

    Reference the Secrets in your values file:

    ```yaml title="my-values.yaml"
    appApi:
      licenseSecret:
        existingSecret: cpki-deployment-license
        key: license-token
    database:
      existingSecret: cpki-db
    redis:
      existingSecret: cpki-redis
    auth:
      existingSecret: cpki-auth
    realtimeGateway:
      existingSecret: cpki-realtime-gateway
      beam:
        cookieSecret:
          name: cpki-beam-cookie
    ```

    The Secret keys are lowercase-hyphenated (`auth-secret`, `database-url`, `runner-auth-secret`); the workloads consume them as the corresponding uppercase env vars (`AUTH_SECRET`, `DATABASE_URL`, `RUNNER_AUTH_SECRET`).

    **Path C — Chart-managed self-hosted secrets (simplest BYOC):**

    Useful when you do not run a secret manager and prefer Helm to create the Kubernetes Secrets directly from values you provide at install time. Set `selfHostedSecrets.enabled: true` and supply the credentials inline:

    ```yaml title="my-values.yaml"
    selfHostedSecrets:
      enabled: true
      # Required issued token; never generated by the chart.
      licenseToken: "<issued deployment license token>"
      db:
        url: "postgresql://user:pass@host:5432/intelligence"
      redis:
        url: "rediss://:password@host:6379"
      auth:
        # Auto-generated when left empty.
        secret: ""
        clientId: "<OIDC client id>"
        clientSecret: "<OIDC client secret>"
      realtimeGateway:
        # Auto-generated when left empty.
        runnerAuthSecret: ""
        secretKeyBase: ""
      beam:
        # Auto-generated when left empty.
        releaseCookie: ""
    ```

    The chart auto-generates `auth.secret`, the realtime-gateway runner/key-base, and the BEAM cookie when those fields are empty. Supply `licenseToken` yourself through a securely managed values file; an empty value leaves the deployment unlicensed.

  </Step>

  <Step>
    ### Install the chart

    The release can be installed directly from the GHCR OCI registry — no local untar is required for the install itself. Use `helm upgrade --install` so the same command works for first-time installs and upgrades.

    ```bash title="Terminal"
    helm upgrade --install copilot-intelligence \
      oci://ghcr.io/copilotkit/charts/intelligence \
      --version <chart-version> \
      -f my-values.yaml \
      -n copilot-intelligence \
      --create-namespace \
      --wait \
      --timeout 10m
    ```

    Layering multiple values files is supported and is the recommended pattern for evaluation: combine the chart's bundled `values-quickstart-local.yaml` (in-cluster Postgres/Redis, eval-sized resources, `migrations.enabled: true`) with the local evaluation overlay above (OIDC, license, Secrets, and ingress). Pull the chart first so you have a local copy of `values-quickstart-local.yaml` to reference:

    ```bash title="Terminal"
    helm upgrade --install copilot-intelligence \
      oci://ghcr.io/copilotkit/charts/intelligence \
      --version <chart-version> \
      -f intelligence/values-quickstart-local.yaml \
      -f my-values.yaml \
      -n copilot-intelligence --create-namespace \
      --wait --timeout 10m
    ```

    `--wait` blocks until the `Deployments` report healthy replicas; `--timeout 10m` allows enough time for image pulls and the initial database migration job. Right-most `-f` files win on conflicts, so put your overlay last.

    <Callout type="info" title="When the migrations Job runs">
    With pre-existing Secrets (Path B), product migrations run **pre-install/pre-upgrade** (weight `-5`). With External Secrets, chart-managed Secrets, or bundled PostgreSQL, they run **post-install/pre-upgrade** (weight `5`): a first install waits for those resources, while upgrades apply the schema before rolling workloads.
    </Callout>

  </Step>

  <Step>
    ### Verify the install

    Check that every pod is `Running` and the ingress is ready:

    ```bash title="Terminal"
    kubectl get pods -n copilot-intelligence
    kubectl get ingress -n copilot-intelligence
    ```

    You should see `app-api`, `app-frontend`, and the default `realtime-gateway` and `embeddings` pods running (unless you disabled the gateway or configured external embeddings). Successful migration hook Jobs may already be removed by Helm; inspect the Helm release status and Job logs if installation fails.

    Confirm the API health check reports `ok`:

    ```bash title="Terminal"
    curl https://<ingress.ui.host>/api/health
    ```

    The endpoint returns `200 OK` only when the database is reachable — a failed health check is almost always a database connectivity problem.

    Service-specific health endpoints, useful when port-forwarding to an individual pod:

    | Service | Path |
    |---|---|
    | `app-api` | `/api/health` |
    | `app-frontend` | `/healthz` |
    | `realtime-gateway` | `/health/live` (liveness), `/health/ready` (readiness) |

    Finally, browse to `https://<ingress.ui.host>` and log in via your OIDC provider. Confirm your mapped organization is available and create or select a project. [Connect your runtime](/intelligence/connect-your-runtime#self-hosted-deployments) using the project API key and your API and realtime base URLs, send a message, and confirm its thread appears in the project.

    <Callout type="info" title="Local validation — port-forward the ingress controller">
    Install with the [local evaluation overlay](#local-evaluation-overlay), which explicitly enables ingress and sets the HTTP browser origin. Port-forward the **ingress controller** so the localhost rule routes `/api` and `/auth` to `app-api`, and leave this terminal open:

    ```bash title="Terminal"
    kubectl -n ingress-nginx port-forward svc/ingress-nginx-controller 8080:80
    ```

    Browse to `http://localhost:8080` and use `http://localhost:8080/api/health` for the API health check. Port-forwarding the `app-frontend` service directly bypasses the ingress and breaks `/api` and `/auth` routing.

    For the runtime persistence check, forward the gateway in a second terminal:

    ```bash title="Terminal"
    GATEWAY_SERVICE=$(kubectl -n copilot-intelligence get service \
      -l app.kubernetes.io/component=realtime-gateway,app.kubernetes.io/instance=copilot-intelligence \
      -o jsonpath='{.items[0].metadata.name}')
    kubectl -n copilot-intelligence port-forward "service/$GATEWAY_SERVICE" 4401:4401
    ```

    A runtime on your host can then use `apiUrl: "http://localhost:8080"` and `wsUrl: "ws://localhost:4401"`. This uses the release name `copilot-intelligence` from the install command; update the label selector if you chose another name.
    </Callout>

  </Step>

## Bundled Keycloak (eval only)

When `keycloak.enabled: true`, the chart deploys the Bitnami Keycloak subchart with a pre-seeded realm and demo user. This is for evaluation and demos — not production. The realm import creates:

- **Realm:** `cpk-dev`
- **OIDC client:** `cpk-self-hosted` with secret `cpk-self-hosted-secret` (override via `auth.keycloakClient.clientId` / `auth.keycloakClient.clientSecret`)
- **Demo user:** `engineer` / `engineer` (override via `auth.keycloakDemoUser`)
- **Redirect URIs / web origins:** default `["*"]` for eval flexibility (override via `auth.keycloakClient.redirectUris` / `webOrigins`)

When `keycloak.enabled: true` and `auth.issuer` is empty, the chart defaults to `http://<release>-keycloak:8080/realms/cpk-dev`. This is a cluster-only service address: the browser cannot complete the OIDC redirect through the application ingress port-forward. Setting `auth.issuer` explicitly overrides the default, but you must separately expose Keycloak, configure its advertised hostname, and make that issuer reachable from both the browser and cluster. The public chart-only local flow above uses an external issuer instead.

For production self-hosted deployments, leave `keycloak.enabled: false` and point `auth.issuer` at your own IdP.

### Analytics (optional)

Product Analytics uses TimescaleDB and is off by default. Create separate Kubernetes Secrets containing a restricted runtime database URL and a schema-owner migration URL. Both use the key `timescale-url`. Enable the pipeline and migration Job together:

```yaml title="my-values.yaml"
analytics:
  enabled: true
  database:
    existingSecret: cpki-analytics-db
  migrations:
    enabled: true
    existingSecret: cpki-analytics-migrator-db
    runtimeRole: cpki_analytics_runtime
```

Create `cpki_analytics_runtime` as the runtime role and use its credentials in `cpki-analytics-db`; the migrations Job grants it access to the Analytics schema and tables. The migration Secret needs the schema-owner credentials. If `runtimeRole` is omitted, the Job grants access to the login role from the runtime URL.

The realtime gateway projects completed runs into TimescaleDB, and App API reads the same store for project metrics. Enabling this pipeline does not backfill old product data. The Analytics migration Job is separate from `migrations.enabled`, which applies the product database schema.

For custom database CAs, use `analytics.database.caBundle` and a database URL with `sslmode=verify-full`. See the pulled chart's `values.yaml` for its Secret/ConfigMap options.
