
## What is this?

The CopilotKit CLI helps you create CopilotKit apps connected to CopilotKit Intelligence, whether cloud-hosted or [self-hosted](/intelligence/self-hosting). It handles browser sign-in, project selection, project-scoped runtime API keys, historical thread import, and local project configuration so your app can use threads and conversation history.

Use the CLI when you want to start a new app, add CopilotKit to an app you already have, find what is wrong with a setup, import historical ADK or LangGraph conversations, or install CopilotKit agent skills for your coding agent.

## Prerequisites

- Node.js 20.19.3+ or 22.13+
- A CopilotKit account for cloud-hosted CopilotKit Intelligence
- An OpenAI API key or another model provider key for the starter app you choose

<Callout type="info" title="Team Self-hosted is a plan">
  Team Self-hosted is the plan for a self-hosted deployment. You choose it on the cloud-hosted account. The deployment uses your identity provider.
</Callout>

## Start a new app

<Callout type="info" title="Creating vs. adding to an existing app">
  `init` (aliased as `create`) scaffolds a brand-new project in its own directory. It prompts for an app name and does not detect or bootstrap an app you already have. To add CopilotKit to an existing app, run [`scaffold`](#add-copilotkit-to-an-existing-app) instead.
</Callout>

<Steps>
  <Step>
    ### Run create

    ```bash title="Terminal"
    npx copilotkit@latest create
    ```

    The CLI prompts for the app name and framework, opens browser sign-in when needed, scaffolds the starter, and connects the app to a cloud-hosted CopilotKit Intelligence project.
  </Step>

  <Step>
    ### Sign up or sign in

    If you are not already signed in, the CLI opens a browser login flow. A new account accepts the CopilotKit Self-Service Agreement. An account that already accepted it does not accept it again.

    If the browser does not open, the CLI prints a login URL and supports a manual paste fallback.
  </Step>

  <Step>
    ### Select or create an organization

    Select or create an organization in the browser. A new organization chooses the Developer plan or a paid plan. Developer is the no-cost plan. Read [Plans](/intelligence/plans) when you want to change that choice.
  </Step>

  <Step>
    ### Return to the terminal

    After organization onboarding, return to the terminal. The original CLI command resumes and prompts you to select or create a project.
  </Step>

  <Step>
    ### Select or create a project

    Choose an existing cloud-hosted project or create a new one. A project is where your app's threads, messages, and platform metadata are stored. To manage projects and API keys in the web app, see [Cloud-hosted CopilotKit Intelligence](/intelligence/managed-intelligence-platform).

    The CLI writes the selected project to `.copilotkit/project.json`:

    ```json title=".copilotkit/project.json"
    {
      "projectId": "proj_...",
      "projectSlug": "support-assistant",
      "clerkOrgId": "org_..."
    }
    ```
  </Step>

  <Step>
    ### Use the generated environment

    `init` and its `create` alias write the cloud-hosted platform URLs, `SL_ENABLED`,
    and project-scoped runtime API key to `.env`.

    ```bash title=".env"
    INTELLIGENCE_API_URL=https://...
    INTELLIGENCE_GATEWAY_WS_URL=wss://...
    CPK_INTELLIGENCE_API_KEY=cpk-...
    CPK_TELEMETRY_ID=...
    SL_ENABLED=true
    ```

    Keep `CPK_INTELLIGENCE_API_KEY` on the server side. The project key connects
    the Runtime to Intelligence. `CPK_TELEMETRY_ID` is an optional, non-secret
    analytics identity.

    Cloud-hosted setup does not issue `COPILOTKIT_LICENSE_TOKEN`. That token
    is only for offline or self-hosted licensing and does not replace the
    cloud-hosted project API key.
  </Step>

  <Step>
    ### Start development

    ```bash title="Terminal"
    npm run dev
    ```

    The starter runs your local app and runtime while storing threads in the cloud-hosted project selected by the CLI.

    Open the app and send a message. The agent answers in the chat. Then run
    `npx copilotkit@latest verify`. When the app is wired correctly, every
    check reports **PASS**.

    To show the threads in your UI, use the [Threads Drawer](/prebuilt-components/copilot-threads-drawer),
    or build your own with [Headless Threads](/headless-threads).
  </Step>
</Steps>

## Add CopilotKit to an existing app

You have an app and you want a working chat in it. `scaffold` adds one with a single command. You do not need a CopilotKit account.

<Steps>
  <Step>
    ### Run scaffold

    Run this command from the folder of your app:

    ```bash title="Terminal"
    npx copilotkit@latest scaffold
    ```

    `scaffold` finds your framework. Then it shows a plan with every file that it will change. Confirm the plan. `scaffold` then adds these parts:

    - The CopilotKit packages.
    - The provider around your app.
    - A chat UI. The default is a popup.
    - A runtime with the built-in agent.

    If a stylesheet resets padding or margin on every element (`* { ... }`) outside a CSS layer, `scaffold` moves that rule into `@layer base`. Otherwise the reset removes the chat's spacing. The plan shows this change before it writes.
  </Step>

  <Step>
    ### Add your model key

    The built-in agent uses `openai/gpt-5-mini` by default. `scaffold` adds an empty `OPENAI_API_KEY` entry to `.env.local` for Next.js, and to `.env` for other frameworks. Put your key in that entry:

    ```bash title=".env"
    OPENAI_API_KEY=sk-...
    ```

    To use a different model, run `scaffold` with `--model <provider/model>`. Then set the key for that provider.
  </Step>

  <Step>
    ### Start the runtime

    The location of the runtime depends on your framework:

    | Framework | Runtime |
    |---|---|
    | Next.js, React Router (framework mode), TanStack Start | A runtime route in your app. It starts with your app. |
    | Vite + React, Create React App, TanStack Router, Vue, Angular, React Native or Expo | A small Node server in `copilotkit/server.mjs`, on port 8200. |

    If your app uses the Node server, start it in a second terminal:

    ```bash title="Terminal"
    npm run copilotkit:runtime
    ```
  </Step>

  <Step>
    ### Send a message

    Start your app. Send a message in the chat. The agent answers.

    If the agent does not answer, run [`doctor`](#diagnose-your-setup-with-doctor).
  </Step>
</Steps>

You can run `scaffold` again at any time. It skips the steps that are already done. If `scaffold` does not recognize the shape of a file, it does not change that file. It lists the edit for that file as a manual step.

| Option | What it does |
|---|---|
| `--ui <ui>` | The chat UI to add: `popup`, `sidebar`, or `chat`. Default `popup`. |
| `--model <provider/model>` | The model that the built-in agent uses. The provider is `openai`, `anthropic`, or `gemini`. Default `openai/gpt-5-mini`. |
| `--dry-run` | Show the plan and write nothing. |
| `--yes` | Apply the plan without the confirm prompt. |
| `--no-install` | Do not install the packages. The next steps show the install command. |

<Callout type="info" title="Frameworks that are not supported yet">
  `scaffold` does not support Nuxt, Remix v2, SvelteKit, or Astro yet. For these frameworks, it reports the framework and writes nothing.
</Callout>

### In a monorepo

Run `scaffold` from the root of the workspace. It reads the workspace config to find your apps. It skips libraries and asks which apps to set up.

To choose an app without the prompt, pass `--app`:

```bash title="Terminal"
npx copilotkit@latest scaffold --app apps/web
```

To set up more than one app, pass `--app` once for each app.

### Run it from a coding agent

If a coding agent runs `scaffold`, `scaffold` does not prompt. Add `--json` to get one JSON object on stdout:

```bash title="Terminal"
npx copilotkit@latest scaffold --json --app apps/web --yes
```

The object has these fields:

- `status`: `completed`, `partial`, `blocked`, or `failed`.
- `plan`: the steps and the files that they change.
- `nextAction`: the next thing for the agent to do.

The exit code gives the same result:

| Exit code | Status |
|---|---|
| `0` | Completed. |
| `1` | Failed. |
| `2` | Blocked. It needs an answer, for example `--app` for a folder with several apps. |
| `75` | Partial. Some steps need a manual edit. |

## Evaluate Intelligence locally

To try Intelligence without a cloud-hosted project, run it in Docker on your own machine. Local evaluation is a preview supported on macOS with Docker Desktop. Read [Evaluate Intelligence locally](/intelligence/self-hosting-local) for the supported preview scope. From your app's folder:

```bash title="Terminal"
npx copilotkit@latest local setup
npx copilotkit@latest local connect --approve-connection
```

The CLI checks Docker, gets an evaluation license for your organization, installs the latest release, and connects the app to it. Read [Evaluate Intelligence locally](/intelligence/self-hosting-local) for requirements, dashboard sign-in, and model setup.

| Command | What it does |
|---|---|
| `npx copilotkit@latest local status` | Shows service health, URLs, and any failed setup step. |
| `npx copilotkit@latest local start` | Starts the app's local stack. |
| `npx copilotkit@latest local stop` | Stops the stack and keeps its data. |
| `npx copilotkit@latest local login` | Opens the local dashboard and signs you in. |
| `npx copilotkit@latest local setup` | Installs the stack, configures the Automatic Learning model, or resumes setup. |
| `npx copilotkit@latest local update` | Updates the stack to the latest release and keeps its data. |
| `npx copilotkit@latest local renew` | Renews the evaluation license. |
| `npx copilotkit@latest local delete` | Asks, then deletes the stack and its data. |

## Diagnose your setup with doctor

If the chat does not answer, run `doctor` from the folder of your app:

```bash title="Terminal"
npx copilotkit@latest doctor
```

`doctor` reads the files in your app and checks these parts:

- The framework and the CopilotKit packages. The packages must be installed and on matching versions.
- The provider, the chat UI, and the runtime. The runtime path in the provider must match the runtime.
- The model key. The key must be set, and it must not be in an env var that the browser can read.
- The TypeScript module resolution, and CORS on the separate runtime server.
- What your framework needs for the chat UI. On the web, no CSS reset such as `* { padding: 0 }` may sit outside a CSS layer, or it removes the chat's spacing. In React Native, `GestureHandlerRootView` must wrap the app, or the chat sheet cannot open.

The checks look at how your framework runs CopilotKit, not at the files that `scaffold` writes. A setup that you wrote by hand also passes.

Every check reports **PASS**, **WARN**, **FAIL**, or **SKIP**. For each failed check, `doctor` prints the fix. Apply each fix, then run `doctor` again.

To also call the running runtime, start your app and add `--live`:

```bash title="Terminal"
npx copilotkit@latest doctor --live --url http://localhost:3000/api/copilotkit
```

| Option | What it does |
|---|---|
| `--live` | Also call the running runtime and check that it answers and allows the app origin. |
| `--url <runtime url>` | The runtime URL that `--live` calls. Without it, `doctor` uses the default URL for your framework and dev port. |
| `--app <path>` | Check only this app. Use it in a monorepo. |
| `--json` | Emit one JSON result on stdout, for coding agents. |

When a check fails, `doctor` exits with code `1`. As a result, it works as a CI gate.

`doctor` checks the files and the model key in your app. To check an app that is connected to a cloud-hosted project, use [`verify`](#verify-your-setup).

## Verify your setup

`verify` checks that your app is wired correctly. It runs from the terminal,
so it also works when there is no browser, for example React Native or a
runtime on a remote host.

```bash
npx copilotkit@latest verify
```

It checks that:

- A cloud-hosted project is selected.
- A project API key authenticates.
- The runtime responds.
- The runtime declares at least one agent.

It reports the runtime version, the agent framework, the gateway wiring, and
the license state.

<Callout type="warn" title="Read the individual checks, not the summary">
  Every check reports **PASS**, **FAIL**, or **UNKNOWN**. `UNKNOWN` means the
  check could not run. It never means the check passed.
</Callout>

To prove the agent actually *runs* rather than that it is *configured*, add
`--round-trip`. It sends one real request through the runtime and reads the
answer back off the thread:

```bash
npx copilotkit@latest verify --round-trip
```

<Callout type="warn" title="What --round-trip does not prove">
  It sends a **fixed** prompt and records the answer's character count and any
  tool-call names, **never the answer's text**. It proves an answer came back;
  it can never tell you what the answer said, so it is no substitute for
  checking a response against the data your project actually holds.

  It also proves an agent answered under the *declared id*, not **which
  deployment** answered. A runtime pointed at another project's agent responds
  identically.

  Because it runs the agent, it costs a model call and records a thread. That is
  why it is opt-in rather than the default.
</Callout>

| Option | What it does |
|---|---|
| `--runtime-url <url>` | The runtime endpoint to probe. Default `http://localhost:3000/api/copilotkit`. Pass this whenever your runtime is elsewhere. |
| `--round-trip` | Also run the agent and read its answer back. |
| `--agent <id>` | Which declared agent to run, when the runtime declares several. |
| `--expect-runtime <mode>` | `intelligence` or `oss`. Without it, an app with no project, no Intelligence key, and no Intelligence client is checked as `oss`. With `oss`, cloud-hosted project and credential checks do not apply, and the command passes only with `--round-trip --agent <id>`. |
| `--timeout <seconds>` | How long to wait for the answer. Default `90`. |
| `--header "<name>: <value>"` | Extra request header, repeatable. Use it when your `identifyUser` reads a session the CLI does not carry. |
| `--json` | Emit a machine-readable payload alone on stdout. |

`verify` exits non-zero unless every check passed, so it works as a CI gate.

## Auth commands

| Command | What it does |
|---|---|
| `npx copilotkit@latest login` | Opens the browser sign-in flow and stores a local CLI session. |
| `npx copilotkit@latest whoami` | Shows the signed-in user and active organization. |
| `npx copilotkit@latest logout` | Clears the local CLI session. |

## Project commands

| Command | What it does |
|---|---|
| `npx copilotkit@latest project select` | Selects or creates a cloud-hosted CopilotKit Intelligence project for the current directory. |
| `npx copilotkit@latest import --source adk --dry-run` | Previews historical Google ADK conversation threads before import. |
| `npx copilotkit@latest import --source langgraph --dry-run` | Previews historical LangGraph conversation threads before import. |
| `npx copilotkit@latest license create` | Issues a CopilotKit license token for flows that still require one. |
| `npx copilotkit@latest license list` | Lists license metadata for the current user or organization. |

Re-running `project select` is safe when you need to move a CLI-created app to a different cloud-hosted project. The command updates `.copilotkit/project.json` and provisions a project-scoped API key for the selected project.
